# ARCHITECTURE.md — шаблон-референс (люди + агенты)

> Источник: [timajwilliams/architecture](https://github.com/timajwilliams/architecture) (architecture.md), дистилляция 2026-07-20.
> Назначение: единый **статичный** документ в корне репо, который свежий разработчик ИЛИ агент читает ПЕРВЫМ, чтобы за минуту понять «где что лежит и что на что влияет».

## Зачем это нам (и чем отличается от codegraph)

| | ARCHITECTURE.md | codegraph |
|---|---|---|
| Тип | статичный committed-документ | динамический запрос по индексу |
| Отвечает на | «что за система, границы, стек, потоки, риски» | «кто вызывает X, blast-radius, где определён» |
| Обновление | вручную при эволюции архитектуры | rebuild индекса |
| Кто читает | человек + агент при онбординге | агент перед правкой конкретного символа |

Они **комплементарны**: ARCHITECTURE.md = карта территории (durable), codegraph = GPS по вызовам (on-demand). Пара «прочитал ARCHITECTURE.md → уточнил codegraph impact» экономит контекст и ловит cross-module связи.

**Ставить в:** крупные репы, куда часто заходят свежие агенты — **YourEduPlatform, ClientProjectB, ClientProjectC** (в первую очередь), далее YourProduct-микросервисы, ClientProjectA, agent-fleet. Мелкие боты/лендинги — НЕ нужно (README хватает).

## Канонический скелет (10 ядровых + 4 для крупных систем)

Копируй в `ARCHITECTURE.md` корня репо, заполняй под проект. Секции 11–14 — опциональны, включай для ClientProjectB/YourEduPlatform/YourProduct-масштаба.

```markdown
# Architecture Overview
<1-2 абзаца: что за система, какую проблему решает, кто/что использует,
 архитектурный стиль (монолит / микросервисы / event-driven / bot-fleet).>

## 1. Project Structure
Аннотированное дерево репо. Для каждой значимой папки — её слой/зона
ответственности. Включи root-файлы, влияющие на build/runtime/deploy
(Dockerfile, package.json, .env.example, миграции, CI-конфиги).

## 2. High-Level System Diagram
Mermaid или текст-схема: актёры/клиенты → приложения → сервисы →
хранилища → внешние API, со стрелками направления данных.

## 3. Core Components
На каждый компонент: Name · Responsibility · важные файлы/папки ·
технологии · runtime-роль · входы/выходы · зависимости ·
где живёт бизнес-логика/состояние/сайд-эффекты.
Подсекции: 3.1 Frontend · 3.2 Backend/API · 3.3 Shared/Common · 3.4 CLI/Scripts.

## 4. Data Flow
Жизненный цикл запроса; ключевые user journeys; read/write-пути;
границы валидации; точки (де)сериализации; error-пути; async/event-потоки.
Для главного runtime-флоу — Mermaid sequence diagram.

## 5. Data Stores
На каждое хранилище: Name · тип (Postgres/Mongo/Redis/S3/Qdrant/…) ·
назначение · ключевые таблицы/коллекции/сущности · границы владения ·
как управляются миграции/схема. Нет персистентности — так и напиши.

## 6. External Integrations / APIs
На каждую интеграцию: сервис · назначение · метод (REST/GraphQL/SDK/
webhook/OAuth/очередь) · где конфигурится/вызывается · авторизация ·
retry/failure-поведение если видно.

## 7. Key Technologies
Языки, фреймворки, runtime, пакет-менеджер, build, тесты, линтеры,
инфра/деплой, observability, архитектурно-значимые библиотеки.
Для каждой — ПОЧЕМУ она важна архитектурно, а не просто «есть».

## 8. Deployment & Infrastructure
Артефакты сборки · модель конфигурации (env vars) · контейнеризация ·
хостинг/таргет · CI/CD · IaC · процесс-модель runtime · допущения о
масштабировании. Не видно из репо — скажи прямо, что осталось узнать.

## 9. Security Architecture
Аутентификация · авторизация · сессии/токены · секреты · валидация
входа · шифрование in-transit/at-rest · CORS/CSP/заголовки · supply-chain ·
trust boundaries · обработка чувствительных данных.
НЕ заявляй контроль, которого нет в коде.

## 10. Monitoring & Observability
Логирование · метрики · трейсинг · error-reporting · health-checks ·
audit-логи · debug-тулинг · дашборды. Минимально/нет — назови пробелы.

## 11. Performance & Scalability   (крупные системы)
Кеш · пагинация · батчинг · фоновая обработка · паттерны запросов к БД ·
оптимизация ассетов · модель конкурентности · известные бутылочные горла ·
лимиты масштабирования. Только подтверждённое кодом/конфигом.

## 12. Testing Strategy   (крупные системы)
Фреймворки · где unit/integration/e2e · фикстуры/моки · стратегия тест-данных ·
запуск в CI · quality-gates · пробелы покрытия.

## 13. Constraints, Risks & Technical Debt   (крупные системы)
Ограничения · tight coupling · дублированные абстракции · недостающие
границы · незавершённые миграции · TODO/FIXME с архитектурным весом ·
операционные риски. На каждый пункт — почему важно и где доказательство в коде.

## 14. Project Identification & Glossary
Имя проекта · назначение · языки · тип приложения · runtime ·
дата последнего архитектурного ревью (сегодня) · команда.
Глоссарий: проектные термины/акронимы/внутренние имена для нового человека/агента.
```

## Правила заполнения (анти-галлюцинации — совпадают с нашими quality-gates)

Это самое ценное из источника. Агенту, генерящему ARCHITECTURE.md, дай эти рамки:

- **Только доказуемое кодом.** НЕ выдумывай сервисы, инфру, деплой-таргеты, БД, очереди, сторонние API, security-механизмы, которых нет в репо.
- **Не определяется из кода → пиши `Not evident from the repository`**, а не догадку.
- **Self-contained.** Никаких «см. файл X» вместо объяснения — вставляй архитектурный факт прямо в документ. Markdown-only, без внешних картинок/ссылок на локальные файлы.
- **Конкретика:** реальные пути, файлы, модули, классы, команды, имена таблиц, точки конфигурации — там, где они видны.
- **Durable > transient:** факты, помогающие понять «где менять и что заденет», важнее сиюминутных деталей реализации.
- **Rationale только если виден** (комментарии/доки/структура). Неясно → `Rationale not documented`. Не сочиняй историю решений.
- **Диаграммы** — Mermaid где полезно (system context, component graph, request/data flow, deployment). Простая архитектура → текст-схема.

### Validation pass (прогнать перед коммитом документа)
- Сверить КАЖДЫЙ названный компонент/сервис/хранилище/интеграцию/технологию с репо.
- Убрать плейсхолдеры и generic-текст шаблона.
- Каждая крупная папка исходников должна где-то фигурировать в документе.
- High-level диаграмма согласована с текстовыми описаниями компонентов.
- Документ отвечает на: **«Где мне внести изменение и что оно затронет?»**
- Если доступны running server / тесты / build output / схема БД / API-схема / Docker — использовать для валидации.

## Рабочий поток «сгенерь ARCHITECTURE.md для репо X» (с codegraph)

1. `cd ${WORKSPACE}/graph-pilot/<name>` → `codegraph status` + `codegraph files` — структура и метрики из индекса (без чтения тонны файлов).
2. `codegraph explore <ключевые области>` — собери реальные символы/связи для секций 3–4.
3. Прочитай root-конфиги (package.json/Dockerfile/.env.example/CI) для секций 1, 7, 8.
4. Заполни скелет выше, соблюдая «Правила заполнения».
5. Прогони Validation pass. Спорные места → `Not evident from the repository`.
6. Положи как `ARCHITECTURE.md` в корень репо (committed, поддерживается со временем).

> Полный prompt-донор для автогенерации (18-секционный, с расширенными подсказками по каждой секции) — в клоне `${WORKSPACE}/temp-clones/architecture/prompt.md`. Наш скелет выше — его lean-дистилляция под 10+4.
