# Промпт-шаблон: завести проект по инженерной дисциплине

Вставлять в НОВУЮ сессию нового проекта. Заменить только `<...>` в первом абзаце.

Отличие от первой редакции (28.08.2026): та заканчивалась словами «пока просто
дай свои мысли, делать будем позже» — и работа не начиналась. Эта редакция —
команда на исполнение, а фазы не переписаны вручную, а отданы скиллу
`project-bootstrap`, который с тех пор написан.

Блок «Определение готового» — не общие слова: каждый пункт стоит там потому, что
на нём уже горели, и рядом сказано, на чём именно.

---

```
Завожу проект по инженерной дисциплине: <что за проект, одной фразой>.
Каталог: <путь>. Состояние: <с нуля | уже есть код, надо привести в порядок>.

Работай автономно до готового результата, не спрашивай разрешения на обратимое.

## 1. Сначала гейт размера, и «нет» — нормальный ответ

Вызови скилл project-bootstrap и пройди его шаг 0. Если проект НЕ большой
(живёт меньше двух недель, к нему не вернутся после перерыва, исполнитель один) —
скажи это прямо, сделай git init + .gitignore + README из трёх строк и
остановись. Каркас, который никто не читает, дороже его отсутствия.

Все три «да» — разворачивай полностью, дальше по этому промпту.

## 2. Интервью — до первого файла

Проведи интервью из скилла: по одному вопросу за раз, размытые ответы не
принимай. Обязательно спроси, что случится, если проект НЕ сделать, и как
отличить сделанное от несделанного — измеримо.

Если проект уже существует, добавь к интервью инвентаризацию БЕЗ ЕДИНОЙ ПРАВКИ:
что вообще есть, где источник истины (частая беда — код в трёх местах разом),
что молча отваливается. Артефакты: INVENTORY.md, RISKS.md. Ничего не чинить на
этом шаге — сначала знать, потом трогать.

## 3. Каркас — по скиллу

git и GitHub до первого содержательного файла, docs/ как карта (а не библиотека),
бэклог в bd, CI как гейт. Всё это в project-bootstrap, шаги 2–6 — иди по ним.

## 4. Дальше — планирование и исполнение чужими скиллами, не импровизацией

- superpowers:brainstorming — ДО первой строки кода, когда задача не однозначна;
- superpowers:writing-plans — план под многошаговую работу;
- superpowers:executing-plans или superpowers:subagent-driven-development —
  исполнение по плану;
- superpowers:test-driven-development — на каждой фиче;
- superpowers:systematic-debugging — на баге, у которого причина не очевидна
  (опечатка и известная гоча чинятся без него);
- superpowers:verification-before-completion — перед словами «готово»;
- superpowers:requesting-code-review — перед вливанием;
- superpowers:using-git-worktrees — когда работа рискует зацепить рабочее дерево.

## 5. Определение готового (DoD) — каждый пункт из набитой шишки

Внеси в docs/DEFINITION-OF-DONE.md и соблюдай сам:

1. ЗЕЛЁНАЯ СТРОКА ОБЯЗАНА ОЗНАЧАТЬ ВЫПОЛНЕННУЮ ПРОВЕРКУ. Не можешь проверить —
   честный skip с причиной; «не смог» и «прошло» считаются РАЗДЕЛЬНО.
   Внутри теста никаких голых return: раннер считает возврат успехом.
2. Тест регистрируется ВСЕГДА, предусловие проверяется ВНУТРИ него.
   `if (условие) { тест }` на чистом чекауте не даёт ни зелёного, ни пропуска —
   строка исчезает, и счёт молча меньше.
3. Каждый новый тест и гейт проверен ОТРИЦАТЕЛЬНЫМ КОНТРОЛЕМ: подложи то, что он
   обязан поймать, и убедись, что он краснеет. Непроверенный гейт — украшение.
4. Утверждение «X не произошло» имеет позитивный контроль: доказательство, что
   код вообще доработал до конца. Иначе отсутствие следа и отсутствие выполнения
   неразличимы.
5. Ответ проверяемой функции ЧИТАЕТСЯ. Многие возвращают {ok:false,error} вместо
   исключения; выброшенный ответ означает падение позже и ПОД ЧУЖИМ ИМЕНЕМ —
   сообщение назовёт не ту причину, и диагноз будет стоить часа.
6. Тест не зависит от среды: сеть, права на системные каталоги, старт процесса
   под нагрузкой. Сбой ЗАПУСКА процесса — не вердикт о коде: одна повторная
   попытка, при втором сбое пропуск с причиной.
7. Верхний порог времени привязан к константе сценария, а не к круглому числу.
   Доказываем «не дожидались вот этого» — порог равен длительности того самого
   «этого».
8. ЗЕЛЁНЫЙ CI НА PR НЕ ОЗНАЧАЕТ ЗЕЛЁНЫЙ main. После КАЖДОГО вливания смотреть
   прогон на самой ветке. Красный main не чинится сам и никого не будит.
9. Любой измеритель внешнего ресурса ОДНОЙ попыткой врёт. Повторять только то,
   что НЕ ответило; ответивший отказом — это факт, а не помеха.
10. Документ, противоречащий коду, опаснее отсутствия документа: по нему считают,
    что механизм работает. У утверждения «так делать нельзя, потому что X»
    спрашивать не «убедительно ли», а «X вообще верно?» — и проверять посылку.

## 6. Границы ролей — иначе проверка проверяет сама себя

- архитектор не пишет код;
- ревьюер не правит то, что ревьюит;
- фиксер не проверяет сам себя;
- РОЙ, КОТОРЫЙ ИЩЕТ, НЕ ИМЕЕТ ПРАВ НА ЗАПИСЬ в рабочее дерево. Запрет в промпте —
  это пожелание, а не права: агент с Write сделает что угодно, и текст «только
  находки» ему не помешает. Ограничивать инструментами или worktree.
- После любого роя — git status ДО коммита, всегда.

## 7. Что считаю сделанным

Каркас развёрнут, первый коммит в GitHub, бэклог заведён, CI зелёный и хотя бы
один его гейт проверен отрицательным контролем, а новый человек (или агент) по
docs/ понимает проект без расспросов — это проверяется онбординг-тестом из
скилла, а не ощущением.

Отчитайся тем, что СДЕЛАНО и чем подтверждено, а не тем, что планируется.
```

## Когда проект уже существует

Первые два шага меняются местами: инвентаризация идёт ДО интервью, потому что
половина ответов уже лежит в коде, и спрашивать о них — терять время владельца.
Правки на этом шаге запрещены полностью: сначала карта, потом руки.
