# Читаемый вектор: ответы Jev как интерпретируемый эмбеддинг

Реализация: `~/.claude/tools/jev_patterns.py` (`Axes`, `Axis`, `profile`, `distance`, `explain`,
`rank_profiles`; команды `profile` и `rank`). Опора — вендор: «заменить или дополнить эмбеддинги» в
`concepts/use-case-map`, а в `cookbooks/autoresearch_feature_discovery` обычный эмбеддинг назван числами
«без вопроса при них». Здесь наоборот: у каждого числа есть вопрос. Идею «Jev как эмбеддер» рассказал Кирен
Клаассен (пересказ — пост Булаева); цифры из того ролика условные, наши — ниже.

## Что это

Каждая **ось** — один вопрос к тексту. Ответ — распределение вероятностей по вариантам этого вопроса
(noul → [нет, да], choice → по вариантам, score → по уровням). Текст превращается в вектор из таких
распределений. Запрос тоже можно задать теми же вопросами и сравнить. Расстояние считается **по вопросам**:
для noul и choice — полное отклонение (TV), для упорядоченных score — нормированное расстояние земляного
движителя (EMD), потом взвешенное среднее. Добавить измерение = добавить вопрос.

Выигрыш против обычного эмбеддинга один, зато настоящий: несовпадение объясняется. `explain(a, b, axes)`
называет вопросы, на которых тексты разошлись сильнее всего, и показывает оба распределения: видно, какой
вопрос «подвёл». Превосходство над обычным эмбеддингом по качеству поиска мы не измеряли.

## Запуск

```bash
python ~/.claude/tools/jev_patterns.py profile --axes axes.json --file note.txt
python ~/.claude/tools/jev_patterns.py rank --axes axes.json --query "..." --docs docs.json --explain -n 5
```

`axes.json` — `{"axes": [{"name", "type": "noul|choice|score", "instructions", ...}]}`; шаблон —
`assets/axes-template.json`. `docs.json` — `{id: текст}`.

Из Python:

```python
import sys; sys.path.insert(0, "~/.claude/tools")
import jev_patterns as jp
axes = jp.load_axes(spec)                                    # или jp.Axes([jp.Axis(name, jev.noul("..."), weight)])
cache = jp.AnswerCache()
docs, errors = jp.profile_many({id: text}, axes, cache=cache)    # параллельно, сбой одного не роняет остальных
q = jp.profile("запрос", axes, mode="want", cache=cache)
jp.rank_profiles(q, docs, axes)                              # [(id, сходство)], лучшее первым
jp.explain(q, docs[id], axes)                                # какие вопросы разошлись
```

## Правила, которые держит код

- **Режим `like`** спрашивает про текст как есть; **`want`** добавляет к вопросу рамку «состояние — это
  запрос, отвечай про документ, который он ищет». Для сравнения запроса с документами берут `want`.
- **Кеш по (текст, вопрос, маршрут, запрошенная модель)** хранит ту модель, что реально ответила. Добавление
  оси задаёт только новый вопрос (на замере второй контроль взял 16 осей из кеша и спросил только две новые), а
  хеш набора осей меняется, и старые профили надо пересобрать, дёшево.
- **Нельзя сравнивать профили разных моделей или разных наборов осей**: `ProfileMismatch`. Известной считается
  только сборка вида `jev-1.13.0`; алиас вроде `jev-latest`, пустое или чужое имя — «неизвестная», такие профили
  тоже не сравниваются. `allow_mix=True` включает сравнение сознательно.
- Хеш набора осей включает имена, вопросы и **порядок вариантов Choice** (от него зависит и ответ, и раскладка
  вектора). Веса осей в хеш не входят: переоценка важности не требует нового профилирования. Если оси правили
  после создания (`axes.axes[i].question` публичный словарь), `questions()` и `distance` откажутся работать.
- `Axes.questions()` отдаёт копии: правка возвращённых словарей хеш и оси не меняет.
- В профиль попадают вероятности и названия осей. `explain` печатает ещё текст вопроса оси, `rank` — id
  документов. Общие правила приватности кеша и ошибок — в `references/pattern-gate.md`.

- **Сигнал настоящий, но не сильный.** Оси по теме дают верную заметку в топ-15 у 12 из 20 вопросов: в этом

- **Контроль не нулевой, причина неизвестна.** У контролей медиана места 56 и 95, а у настоящих осей 10. Оси
  не по теме всё же дают немного больше случайного (4 и 5 против 3,40 в топ-15); чем именно (регистр, длина,
  «техническое или нет»), мы не измеряли. Поэтому нельзя утверждать, что сигнал целиком из смысла вопросов.
- **Режимы `want` и `like`:** в одном прогоне агрегаты близки (6/9/12 против 7/8/11); по вопросам `want` лучше
  в 9, хуже в 7, поровну в 4. Устойчивого преимущества не установлено, разброс прогона мы не измеряли.
- **Где работает.** Широкие темы (20 и больше подходящих заметок, таких вопросов 9): верная заметка в топ-5 у
  3 из 9, в топ-15 у 8 из 9 (места 1, 10, 6, 16, 6, 1, 12, 6, 1). Одиночные цели: ни один из пяти вопросов с 1–5
  подходящими заметками не попал в топ-15 (места 648, 25, 66, 237, 503 из 2030). Там, где подходящих 6–8, места
  19, 10, 4, 3: заметно лучше случайных 226–290.
- **С лексикой не сравнить напрямую и проигрывает.** Лексика даёт 15 из 20, но ей засчитывалось всё, что
  напечатал `memory_find` (имена и фрагменты), а вектору — только имя и описание первых заметок. Честное
  сравнение требует общего критерия и одинакового числа результатов. Порядок величин ясен: эти общие оси
  недостаточны для части точечных запросов. **Поиск по памяти вектор не заменяет.**

## Где брать

- Небольшой корпус (десятки или сотни) и оси, написанные под его предметную область.
- Нужно объяснить несовпадение («почему эти два письма не одно и то же»): `explain`.
- Классификация, поиск дублей, слежение за дрейфом набора текстов, фильтр перед дорогим шагом.

Где не брать: большой корпус без доменных осей; место, где нужен чистый поиск по ключевым словам; всё, что
требует счёта и дат (в код).

## Не проверено

Вектор как переранжировщик поверх кандидатов лексического поиска; оси под предметную область (30–60 вопросов
вместо 18 общих); стабильность при смене сборки Jev; влияние весов; другие корпуса и другие наборы вопросов
(здесь один корпус и двадцать вопросов, один прогон); влияние длины и регистра заметок на результат; независимость
критерия «верная заметка» от осей.
