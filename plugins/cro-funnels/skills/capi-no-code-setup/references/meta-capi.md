# Meta CAPI — детальный setup

> ⚠️ Meta признана экстремистской в РФ. Раздел — для международных/СНГ-проектов.
> Источник: экспертная методология («Пиксель, настройка событий, Events Manager») + общеизвестная практика Conversions API.

CAPI (Conversions API) передаёт в Meta **серверные** события, которые браузерный пиксель физически не видит: лид, квалификацию, звонки, продажи, LTV. Критичен при длинном цикле сделки — продажа происходит через недели после клика, пиксель её уже не свяжет с рекламой.

---

## 1. Что передаёт CAPI

| Событие | Откуда берётся |
|---------|----------------|
| `Lead` | заявка с сайта / форма (дублирует пиксель — для дедупликации) |
| квалификация (кастомная конверсия) | смена статуса в CRM на «квалифицирован» |
| звонок (кастомная конверсия) | телефония / статус в CRM |
| `Purchase` | оплата (платёжка / статус сделки) |
| LTV (значение в `Purchase` / кастомной) | сумма повторных оплат из CRM |

**Правило:** максимально использовать **стандартные** события (Meta их понимает лучше всего); **кастомные** — только для глубоких этапов (квал-лид, звонок, оплата). Не дублировать стандартное событие кастомным без необходимости.

---

## 2. Семь параметров матчинга

Чем больше совпадений — тем точнее Meta «склеит» серверное событие с конкретным пользователем (выше Event Match Quality → лучше оптимизация и lookalike).

| Параметр | Что это | Хешируется? | Источник |
|----------|---------|-------------|----------|
| `email` (`em`) | email лида | **да, SHA-256** | форма / CRM |
| `телефон` (`ph`) | телефон лида | **да, SHA-256** | форма / CRM |
| `страна` (`country`) | гео-привязка | **да, SHA-256** | CRM / IP |
| `zip` (`zp`) | индекс | **да, SHA-256** | CRM |
| `External ID` (`external_id`) | внутренний ID пользователя/лида в твоей системе | **да, SHA-256** | CRM (`user_id`/`lead_id`) |
| `FBC` (`fbc`, Facebook Click ID) | ID клика по рекламе — связывает событие с конкретным объявлением | **нет** | cookie `_fbc` |
| `FBP` (`fbp`, Facebook Browser ID) | ID браузера — связывает с сессией пользователя | **нет** | cookie `_fbp` |

> **Принцип (экспертная методология):** Meta должна знать, **какие лиды оказались качественными**, чтобы оптимизироваться на нужных людей. Все 7 параметров нужны для качества — отправляй максимум того, что есть.

### Почему FBC/FBP критичны
- `FBC`/`FBP` — единственные параметры, которые **прямо** связывают серверное событие с **конкретным кликом по рекламе**. Email/телефон дают вероятностный матчинг по экосистеме Meta; FBC/FBP дают детерминированную связь.
- Их нужно **захватить при заходе пользователя** (cookies `_fbc`, `_fbp` ставит пиксель) и **сохранить в CRM** вместе с лидом, чтобы потом, при оплате через недели, прокинуть в серверное событие.
- Если FBC/FBP не сохранены — матчинг идёт только по хешам email/телефон (хуже, но работает).

## 3. Хеширование и нормализация

PII (email, телефон, имя, страна, zip, External ID) **нельзя отправлять в открытом виде** — только SHA-256. Перед хешированием — нормализовать, иначе хеши не совпадут с тем, что Meta вычислит на своей стороне.

| Поле | Нормализация перед SHA-256 |
|------|----------------------------|
| `email` | trim, нижний регистр: `john@example.com` → `john@example.com` |
| `телефон` | только цифры с кодом страны, без `+`/пробелов/скобок: `+1234567890` → `79151234567` |
| `страна` | ISO-код в нижнем регистре: `Russia` → `ru` |
| `zip` | нижний регистр, без пробелов: `01310-100` → `01310100` (для РФ — 6 цифр) |
| `External ID` | как есть в системе, но стабильный (тот же ID при браузерном и серверном событии) |

> Большинство no-code инструментов и нативных коннекторов (HubSpot, Zapier Facebook CAPI action) **хешируют автоматически** — нужно лишь подать нормализованное значение. В n8n/Make хеширование делаешь сам (нода Crypto / функция). **Не хешируй дважды** (двойной SHA-256 = промах матчинга).

## 4. Структура события (payload)

Минимальный server-side event для Meta:

```
event_name   : "Purchase"            // или Lead / кастомная
event_time   : 1719000000            // Unix-время момента события (НЕ момента отправки)
event_id     : "order_12345"         // КЛЮЧ дедупликации с пикселем
action_source: "website" | "system_generated" | "phone_call" ...
user_data    : {
    em          : [sha256("john@example.com")],
    ph          : [sha256("79151234567")],
    country     : [sha256("ru")],
    zp          : [sha256("00000000")],
    external_id : [sha256("user_789")],
    fbc         : "fb.1.1719000000.AbCd...",   // НЕ хешируется
    fbp         : "fb.1.1719000000.1234567890" // НЕ хешируется
}
custom_data  : { value: 4900, currency: "RUB" }   // для Purchase
```

- `event_time` — время **самого события**, не отправки. Meta принимает события задним числом (важно для офлайн-конверсий: оплата вчера, отправка сегодня).
- `action_source` — где произошло: `website` (веб), `system_generated` (CRM-автоматика), `phone_call` (звонок), `physical_store` (офлайн).

## 5. Event ID — дедупликация browser + server

При правильной настройке одно действие (например, покупка) генерирует **два** события: браузерное (пиксель) и серверное (CAPI). Без общего ключа Meta посчитает их за две покупки.

**Решение:** браузерное и серверное события одного действия отправляются с **одинаковым `event_id`**. Meta схлопывает дубли.

```
Пиксель (браузер):   fbq('track','Purchase',{...}, {eventID: 'order_12345'})
CAPI (сервер):       event_id: 'order_12345'   ← ТОТ ЖЕ
```

- `event_id` должен быть **детерминированным** (один и тот же для обоих каналов) — обычно ID заказа/сделки из CRM.
- Дедупликация работает по паре **`event_id` + `event_name`** в окне времени.
- **Если видишь задвоение в Test Events** — первым делом проверяй, что `event_id` совпадает у пикселя и CAPI. Это самая частая боль.

> Зачем вообще слать оба, если потом схлопывать? Подстраховка: если пиксель срежет блокировщик/ITP — событие всё равно придёт с сервера. Если оба прошли — дедупликация оставит одно.

## 6. Test Events — обязательная проверка

Раздел **Events Manager → Test Events** тестирует поток в реальном времени.

**Процедура:**
1. Открыть сайт через **тестовый режим** (Test Events даёт код для подстановки).
2. Пройти всю воронку: просмотр → форма → оплата.
3. Параллельно проверить серверные события (триггернуть смену статуса/оплату в CRM).
4. Убедиться, что события отбились корректно.

**Критерии корректной настройки:**
- ✅ **нет дублей** событий;
- ✅ события приходят **ровно один раз** (browser + server схлопнулись по Event ID);
- ✅ данные идут **стабильно и равномерно**;
- ✅ **веб-события + серверные события** (CAPI) отображаются корректно и не задваиваются между собой.

---

## 7. Event Match Quality — проверка матчинга

После запуска в Events Manager у каждого события есть **Event Match Quality** (качество совпадения) — насколько хорошо Meta смогла сматчить серверные события с пользователями.

- Растёт с числом и качеством параметров матчинга (особенно email + телефон + FBC/FBP).
- Низкий EMQ → проверь: нормализацию (хеши не совпадают?), сохраняются ли FBC/FBP, не хешируются ли FBC/FBP по ошибке, не хешируется ли что-то дважды.
- Цель — **передавать максимум** из 7 параметров; не ограничиваться только email.
