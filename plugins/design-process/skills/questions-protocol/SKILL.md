# Questions protocol

Дизайн без контекста = дизайн в стол. Вопросы — дешевле переделок.

## Когда спрашивать

| Запрос | Спрашивать? |
|---|---|
| «Сделай дек на 6 слайдов по этому PRD» | Нет — делать |
| «Поправь отступы в хедере» | Нет — делать |
| «Сделай прототип онбординга для доставки» | **Да, много** |
| «Сделай дек по теме онбординга» | Да, минимум 4 вопроса |
| «Сделай дизайн страницы тарифов» | Да, 2-3 вопроса |
| «Перерисуй вот этот макет, добавь dark mode» | Нет — делать |

**Правило:** если можешь представить 2+ радикально разных результатов на этот запрос — спрашивай.

## Минимальный пакет вопросов (большая задача)

Задавай списком, не по одному. Жди один ответ — потом за работу.

```
1. Стартовая точка: дизайн-система / UI-кит / кодовая база / скриншоты — что есть?
2. Целевая платформа: web (desktop/tablet/mobile?) / iOS / Android / print?
3. Тон визуала: «по учебнику», «brand-loyal», экспериментальный?
4. Стиль-референс: ссылка на сайт / app / Dribbble pin, в стиле которого делать?
5. Содержание: ключевые блоки / экраны / последовательность?
6. Состояния: empty / loading / error / disabled — нужны?
7. Адаптив: только desktop, или mobile тоже?
8. Output: один HTML / PDF / PPTX / package для разработчика?
```

Не все 8 — берёшь 3-5 самых релевантных. Например, для лендинга не спрашивать про «состояния», для онбординга — наоборот, обязательно.

## Что НЕ спрашивать

- Очевидное из брифа («ты сказал 6 слайдов» → не спрашивай «сколько слайдов»)
- Вопросы, ответ на которые ничего не меняет в результате
- 10+ вопросов сразу — отпугивает, юзер не отвечает
- Вопросы про вкус («какие цвета вам нравятся?») — давай 2-3 опции и спроси «какая ближе»

## Хорошие vs плохие формулировки

| Плохо | Хорошо |
|---|---|
| «Какой стиль вы хотите?» | «По стилю как Linear / Stripe / Vercel — на какой ближе?» |
| «Сколько секций нужно?» | «У меня в голове 5: hero, features, pricing, FAQ, CTA. Что добавить или убрать?» |
| «Какие цвета?» | «Бренд: указан ли в Figma / на сайте? Если нет — давай deep navy + cyan accent» |
| «Когда нужно?» | (не спрашивай — у тебя нет дедлайна) |

## Когда задавать вопросы посреди работы

Можно и нужно, если:
- Открылась развилка с двумя одинаково правильными путями
- Бриф противоречит сам себе («минимализм + 6 акцентных цветов»)
- Юзер прислал референс, но он не вписывается в его же бренд

Формат: одна фраза-вопрос, две альтернативы, одна рекомендация.

```
«Заметил, что бренд cream/navy, а в референсе яркие неоновые акценты.
Идём в (а) бренд и убираем неон, или (б) делаем гибрид «navy базис + неон micro-accent»?
Я бы рекомендовал (б) — современнее, но узнаваемо. ОК?»
```

## Что делать, если юзер не ответил

- Ждать максимум 1 раунд. Не задавай тех же вопросов повторно.
- Берёшь разумные дефолты, явно фиксируешь их в начале работы:
  ```
  «Юзер не уточнил — иду по дефолтам:
    — desktop 1440 only
    — стиль editorial monochrome
    — output: один HTML
  Если что-то не так — скажи, перепишу.»
  ```
- Делаешь задачу. После показа результата — юзер или одобрит или скорректирует.

## Антипаттерны

- Лавина из 12 вопросов в первом сообщении → юзер закрывает чат
- Вопросы про реализацию вместо вопросов про намерение («какой framework?» вместо «куда это пойдёт?»)
- Вопросы про вкус без альтернатив («какой шрифт?») вместо («Inter / Manrope / Helvetica — какой?»)
- Спрашивать после того, как уже начал делать
- Не зафиксировать ответы в начале артефакта (комментарий в HTML или sidebar в design-canvas)
