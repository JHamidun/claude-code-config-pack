# Реализация RevOps в CRM (маппинг процесс → API)

Этот скилл (`revops-ru`) задаёт **что** настроить в воронке. Здесь — таблица «элемент RevOps → что для него есть в CRM».

Конкретные имена методов ниже — из REST API **Битрикс24** (она распространена в РФ, документация открытая). У amoCRM, HubSpot и Pipedrive устроено так же по смыслу: лид, сделка, воронка со стадиями, пользовательские поля, роботы/автоматизации, вебхуки. Читай левую колонку как задачу, правую — как образец того, что искать в документации своей CRM. Какая CRM у тебя (и есть ли она вообще) — раздел «Учёт и аналитика» в `~/.claude/business-context.md`; ответ «CRM нет, ведём в таблице» тоже рабочий: тогда стадии и SLA живут в колонках таблицы, а роботов заменяет `n8n`.

Вход лидов и B2C-воронка часто живут не в CRM, а в **продуктовой БД** (регистрации, trial, оплаты). Тогда CRM держит только B2B-сделки, а связь между ними — вебхук или `n8n` как glue.

> Правило: не писать здесь API-клиенты. Описать конфигурацию словами — конкретные поля, стадии, триггеры — и отдать её в настройку CRM или в `n8n`.

## Объекты CRM

| RevOps-понятие | Сущность CRM | Пример метода (Битрикс24) |
|---|---|---|
| Подписчик / Лид | **Лид** (CRM Lead) | `crm.lead.add/update/list` |
| MQL → SQL конвертация | **Лид → Сделка + Контакт + Компания** | `crm.lead.add` → конвертация в `crm.deal.add` |
| Сделка | **Сделка** (CRM Deal) в воронке | `crm.deal.add/update/list`, `crm.dealcategory` (воронки) |
| Стадии сделки | **Стадии воронки** (deal stages) | `crm.dealcategory.stage.list`, `crm.status` |
| Компания (ИНН) | **Компания** (CRM Company) | `crm.company.add/update` |
| ЛПР | **Контакт** (CRM Contact) | `crm.contact.add/update` |

## Поля и скоринг

| Элемент | Как в CRM |
|---|---|
| Fit-скор / Engagement-скор | **пользовательские поля** (в Битрикс24 — `UF_`) на Лиде/Сделке (число) — `crm.lead.userfield.add` |
| Источник лида + дата (152-ФЗ lineage) | стандартные `SOURCE_ID` + пользовательское поле «источник_URL», `DATE_CREATE` |
| Грейд (A/B/C/D) | пользовательское поле или вычисляется роботом/автоматизацией |
| Обязательные поля на стадию | проверка в **автоматизации** на смене стадии (блокировать переход) |

## Хэндофф и SLA (автоматизации)

| RevOps-механизм | Реализация (в Битрикс24 — scope `bizproc` / `im`) |
|---|---|
| MQL → мгновенный алёрт менеджеру | **Робот/бизнес-процесс** на достижении порога скора → уведомление в чат (`im.notify`) + создание задачи |
| Задача с SLA 4ч | `tasks.task.add` с дедлайном; робот на стадии MQL |
| Эскалация при просрочке | процесс с таймером → уведомление руководителю при превышении SLA |
| Маршрутизация (round-robin/по сегменту) | правило назначения ответственного в роботе (по отрасли/размеру → старший менеджер для enterprise) |
| Recycling с кодом причины | смена стадии Лида на «Recycled» + поле «код_причины»; робот ставит в нуртур-сегмент |

## Уведомления и автоматизация

| Сценарий | Метод (пример Битрикс24) |
|---|---|
| Уведомление о новом MQL | `im.notify.personal.add` или робот |
| Авто-смена стадии при условии | бизнес-процесс (`bizproc.*`) |
| Алёрт по застрявшей сделке | процесс с таймером (2× средних дней стадии) |
| Дайджест активности по горячим лидам | задача/отчёт по расписанию |

## Метрики (отчёты)

| Метрика | Источник |
|---|---|
| Конверсия по стадиям, win rate, скорость | встроенная **аналитика CRM** / выгрузка сделок + агрегация |
| Speed-to-lead | разница между созданием лида и первой активностью |
| Воронка marketing→sales | отчёт по стадиям Лид→Сделка |
| free→trial→paid (B2C) | НЕ в CRM — продуктовая БД + веб-аналитика |
| контент→продукт-trial | продуктовая БД (`newsletter_subscribers`→`leads`/trial) + веб-аналитика |

## Синхронизация входа лидов

- **Один вход для всех лидов.** Где он — решается в `business-context.md` → «Учёт и аналитика»: продуктовая БД (если есть свой продукт с регистрацией), CRM или таблица. Двух входов быть не должно, иначе один из них молча отстанет.
- Формы с сайта → лид во вход; при B2B-квалификации зеркалится в сделку CRM. Интеграция — вебхук CRM или `n8n` как glue.
- Каждый лид несёт источник + дату + UTM (152-ФЗ lineage + атрибуция).
- Касания из `draft-outreach` (email/LinkedIn/Telegram) фиксируются как **активности**: в Битрикс24 это `crm.activity.add`, в продуктовой БД — таблица вида `conversations`.
- Бронь консультации — `zoom` → запись в таблицу встреч.

## Порядок внедрения

1. **Определить** (этот скилл): стадии, скоринг, SLA, коды отклонения — на бумаге.
2. **Согласовать** маркетинг ↔ продажи (определения MQL/SQL для обеих воронок).
3. **Вход** — форма/бот → единая точка приёма. **B2B-сделки** — настроить в CRM: воронка + стадии → поля скоринга → автоматизации (алёрты, SLA-таймеры, recycling) → обязательные поля.
4. **Построить мостик** контент→продукт-trial nurture (главная дыра воронки).
5. **Дашборды**: CRM (B2B) + продуктовая БД + веб-аналитика (B2C).
6. **Калибровать** скоринг квартально по выигранным сделкам и trial→paid конверсии.
