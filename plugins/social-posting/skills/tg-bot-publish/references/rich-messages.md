## 1. Когда брать rich, а когда обычный пост

| Берём rich | Берём обычный `send` |
|---|---|
| таблица, чек-лист, раскрывающийся блок, формулы | простой пост с картинкой и кнопкой |
| длинный текст: до 32768 знаков против 4096 | текст надо дать скопировать целиком |
| несколько картинок в теле поста, коллаж, слайдшоу | важна максимальная совместимость клиентов |
| кнопки внутри текста, а не только под ним | пост в канал, где нужна живая ветка комментариев |

**Про ветку комментариев.** Запрета на rich в канале с обсуждениями нет —
`sendRichMessage` прямо принимает канал. Ветку ломает не rich, а кнопка под постом:
📎 карточка [bugs.telegram.org/c/41803](https://bugs.telegram.org/c/41803) (Closed ·
Issue · General) с ответом администрации «This is the expected behavior at the moment.
It may change in future» — «if a post with an inline keyboard button is sent, the
comments will not be displayed in the channel». 🧪 Наша отправка 03.09.2026 дала то же
самое ([[tg-inline-button-kills-comments-2026-09-03]]). 💭 Про кнопки ВНУТРИ
rich-блока (`<tg-button-row>`) данных нет — на ветку они, возможно, не влияют, но это
не проверено.

**Про копирование.** ❓ На Android текст rich-сообщения не скопировать вовсе — в меню
нет пункта «Копировать» (📎 /c/63413, **Suggestion**, Open); на iOS не работает
копирование кода по нажатию (📎 /c/63502, Suggestion, Open). Про Desktop, macOS и Web
данных нет, в документации про копирование rich-текста не сказано ничего.

## 2. Отправка

```bash
python ~/.claude/tools/tg_bot.py --token <ИМЯ> rich --to @канал --md-file post.md \
  --btn "Записаться|https://t.me/bot?start=src"      # обычная кнопка ПОД постом
```

Payload: `{"chat_id": …, "rich_message": {"markdown": "…"}}`. В `InputRichMessage`
ровно одно из полей `html`, `markdown`, `blocks` (10.2). Плюс `media`, `is_rtl` и
`skip_entity_detection` — последнее выключает автоопределение сущностей: голых URL,
e-mail, @упоминаний, хэштегов, кэштегов, команд бота, телефонов и номеров банковских
карт (карты названы во вводном разделе; в описании самого поля их нет).

Параметры `sendRichMessage`: `reply_markup`, `disable_notification`, `protect_content`,
`message_effect_id` (только личные чаты), `allow_paid_broadcast` (раздел 10),
`reply_parameters` (ответ и цитирование), `ephemeral_message_parameters` (10.3),
`business_connection_id`, `message_thread_id`, `direct_messages_topic_id`,
`suggested_post_parameters` (только direct messages chats — так Bot API зовёт чаты
личных сообщений канала).

🚨 Два параметра в рассылке понимают неправильно:

- **`ephemeral_message_parameters`** — это не «исчезающая рассылка», а личный ответ
  ОДНОМУ участнику внутри группы или супергруппы (адресат — `receiver_user_id`,
  остальные его не видят). Отправить можно только в течение **15 секунд** после
  действия пользователя: нужен `callback_query_id` из нажатия кнопки или ответ на его
  эфемерное сообщение (`reply_parameters.ephemeral_message_id`). Бот-администратор
  чата может слать такое любому участнику-человеку в любое время. Живёт сообщение
  неопределённо: «may disappear automatically after some time, or if the app is
  restarted». Доставка прямо объявлена негарантированной, особенно если получатель
  офлайн.
- **`business_connection_id`** — сообщение уходит от имени бизнес-аккаунта, и rich так
  отправляется, только если сам владелец аккаунта может отправлять rich-сообщения
  («Bot can send rich messages on behalf of a business account only if the owner of the
  business account can send rich messages»); кто именно может — в доках не сказано.
  Там же свои ограничения на кнопки (раздел 5).

💭 `reply_markup` (клавиатура под постом) и кнопки внутри тела в одном вызове
документация не запрещает и не описывает: у метода есть и `rich_message`, и
`reply_markup`, оговорок о сочетании нет. ❓ Совместной отправкой это **не проверено**
— 14.09.2026 кнопка в теле и `--btn` уходили разными сообщениями. Перед рассылкой
отправить одну пробу себе с обоими и посмотреть глазами.

Правка уже отправленного: `editMessageText` с `rich_message` вместо `text` (10.1).

## 3. Синтаксис

**Markdown совместим с GitHub Flavored Markdown «where possible»** и допускает
произвольный HTML. Оговорка не формальная: у части возможностей markdown-формы нет
вовсе — «For formatting features that don't have Markdown syntax, use HTML tags».
Синтаксис MarkdownV2 сюда тоже не переносится: `**>` (сворачиваемая цитата) в Rich
Markdown не описан, `__…__` здесь жирный, а не подчёркнутый, зачёркнутый — `~~…~~`.

🚨 **Внутри блочных HTML-тегов markdown НЕ разбирается** — кроме `<details>`,
`<tg-collage>`, `<tg-slideshow>`. В `<blockquote expandable>`, `<aside>`,
`<tg-button-row>` форматировать только тегами.

Блоки:

| Что | Markdown | HTML |
|---|---|---|
| абзац | пустая строка между | `<p>` |
| заголовок h1–h6 | `#`…`######` | `<h1>`…`<h6>` |
| разделитель | `---` | `<hr/>` |
| список, нумерованный | `-`, `1.` | `<ul>`, `<ol start type reversed>`, `<li value type>` |
| чек-лист | `- [ ]`, `- [x]` | `<li><input type="checkbox" checked>` |
| цитата | `>` | `<blockquote>…<cite>Автор</cite>` |
| сворачиваемая цитата (10.3) | — только HTML | `<blockquote expandable>` |
| врезка по центру | — только HTML | `<aside>…<cite>` |
| подвал | — только HTML | `<footer>` |
| раскрывающийся блок | — только HTML | `<details open><summary>…</summary>` |
| таблица | `\| a \| b \|` | `<table bordered striped compact><caption>`, ячейки с `colspan rowspan valign` |
| код | ``` с языком | `<pre><code class="language-python">` |
| формула | `$$…$$` или ```` ```math ```` | `<tg-math-block>` |
| карта | — только HTML | `<tg-map lat long zoom>` |
| коллаж, слайдшоу | — только HTML | `<tg-collage>`, `<tg-slideshow>` |
| файл (10.3) | `![](url.zip "подпись")` | `<tg-document src>` |
| ряд кнопок (10.3) | — только HTML | `<tg-button-row align="center">` |

**Размер заголовка** — это поле `size` у блока `InputRichBlockSectionHeading` (так он
зовётся при отправке в режиме `blocks`; в ответе тот же блок — `RichBlockSectionHeading`),
а НЕ атрибут HTML-тега: «1-6, **1 is the largest**, 6 is the smallest». Легко
перепутать с номером `<h1>`…`<h6>`.

Inline: `**жирный**`, `*курсив*`, `~~зачёркнутый~~`, `` `код` ``, `==маркер==`,
`||спойлер||`, `$формула$`, ссылки `[текст](url)`, сноски `[^id]` с определением
`[^id]: текст`, кастомное эмодзи `![👍](tg://emoji?id=…)`, упоминание
`[текст](tg://user?id=…)`, хэштег `\#хэштег`.

🚨 В скобках у кастомного эмодзи стоит **обычное эмодзи-замена, а не пробел**: пустые
скобки `![](…)` в Rich Markdown означают медиа-блок. В режиме `blocks` это
обязательное (не Optional) поле `alternative_text` — «Alternative emoji for the custom
emoji»; оно же считается в лимит знаков.

**Markdown-формы нет как минимум у этих** — в доках список дан примером, без слова
«все»: `<u>` / `<ins>`, `<sub>`, `<sup>`, `<a name>`, `<aside>`, `<details>`,
`<tg-map>`, `<tg-collage>`, `<tg-slideshow>` и кнопки `<tg-button>` /
`<tg-button-row>` (плюс `<tg-thinking>` — только в `sendRichMessageDraft`).
💭 Список неполный: в Rich HTML есть и то, чего в синтаксисе Rich Markdown нет вовсе —
`<footer>`, `<blockquote expandable>`, `<cite>`, атрибуты таблиц и списков.
У `<mark>`, `<tg-spoiler>` и `<tg-emoji>` формы, наоборот, ЕСТЬ — `==…==`, `||…||`,
`![👍](tg://emoji?id=…)`, и тянуть их тегом незачем.

**Дата и время получателя:**
`<tg-time unix="1647531900" format="wDT">22:45 tomorrow</tg-time>`, markdown-форма —
`![22:45 tomorrow](tg://time?unix=1647531900&format=wDT)`.

Формат — не список из трёх слов, а строка по регулярному выражению `r|w?[dD]?[tT]?`:
`r` — время относительно текущего, ни с чем не сочетается; `w` — день недели;
`d`/`D` — дата коротко/длинно («17.03.22» / «March 17, 2022»); `t`/`T` — время
коротко/длинно («22:45» / «22:45:00»). Порядок задан выражением: `wDT` и `dt` валидны,
`Tw` — нет. Доки говорят про **локальный формат и язык получателя**; слова «часовой
пояс» там нет.

🚨 **«Формата по умолчанию» не существует.** Текст внутри тега — это обычный текст
сообщения: без `format` он показывается как есть, с `format` клиент подменяет его
датой. Писать туда осмысленное время, а не заглушку. 📎 Для ответов с цитированием
важно: `quote` обязан совпасть с текстом посимвольно (core.telegram.org/api/entities).

💭 **Кастомное эмодзи** (`tg://emoji`, `<tg-emoji emoji-id="…">👍</tg-emoji>` или
`<img src="tg://emoji?id=…" alt="👍"/>`): внутрь класть обычное эмодзи. Для rich доки
этого прямо не требуют — вывод наш, но опора твёрдая: поле зовётся `alternative_text`,
в примерах всюду стоит настоящее 👍. Дословное требование живёт в обычном
форматировании: «A valid emoji must be used as the content of the tg-emoji tag».

⚠️ Ограничение Fragment/Premium («can only be used by bots that purchased additional
usernames on Fragment or in the messages directly sent by the bot to private, group and
supergroup chats if the owner of the bot has a Telegram Premium subscription») стоит у
кастомных эмодзи вообще — и у `icon_custom_emoji_id`. Само это поле к rich отношения
не имеет: оно есть только у кнопок обычной клавиатуры (`InlineKeyboardButton`,
`KeyboardButton`), а у кнопок ВНУТРИ rich (`RichMessageButton`) его нет — там
кастомное эмодзи кладётся прямо в текст кнопки.

**Экранирование.** Полного списка спецсимволов, как у MarkdownV2, у Rich Markdown нет,
а произвольный HTML разрешён. 💭 Опасен не любой `<`, а тот, что складывается в
ПОДДЕРЖИВАЕМЫЙ тег («a<b>c», `<i>` из чужого текста, вставленный кусок HTML): по
правилам GFM имя тега начинается с ASCII-буквы, поэтому «<3», «a<b», «<не указано>»
тегами не считаются. Но оговорка «where possible» гарантий не даёт, а поведение
сервера на живой `<` не описано вообще — в отличие от обычного `parse_mode=HTML`, где
правило «All <, > and & symbols that are not a part of a tag … must be replaced»
стоит прямо. 🚨 Безопасно: писать `&lt;` и прогонять текст от людей через проверку
разбора (раздел 9). Экранирование `\#` документировано — оно прямо в списке синтаксиса.

Именованные HTML-сущности в поле `html` поддержаны только эти: `&lt; &gt; &amp; &quot;
&apos; &nbsp; &hellip; &mdash; &ndash; &lsquo; &rsquo; &ldquo; &rdquo;` (числовые —
любые). 💭 Про сущности в поле `markdown` доки не говорят ничего.

## 4. Картинки и файлы

- 🚨 **Право бота на медиа — условие всего вызова:** «If the message contains a block
  with a media element, then the bot must have the right to send the media to the
  chat». 💭 Что падает весь вызов, а не деградирует до текста, доки не пишут — но
  условие сформулировано для метода целиком.
- Отдельного права именно под rich нет: в группах и супергруппах rich покрыт общим
  `can_send_messages` («text messages, **rich messages**, contacts, giveaways…»), в
  канале бот постит по админскому `can_post_messages`. А право на медиа — это
  отдельные `can_send_photos` / `can_send_videos` / `can_send_documents` /
  `can_send_audios`, и `can_send_messages` их НЕ включает.
- **Медиа — всегда отдельный блок.** Внутрь абзаца картинку не поставить.
- По ссылке — только HTTP/HTTPS. Тип определяется по MIME и адресу.
- ✅ **Проверено нашей отправкой 25.09.2026:** `media` — МАССИВ объектов `InputRichMessageMedia` вида `{"id": "cover", "media": {"type": "photo", "media": "attach://cover"}}` (файл — multipart-полем `cover`), в markdown — `![](tg://photo?id=cover)`. Ошибки на других формах: объект вместо массива → «expected an Array of InputRichMessageMedia»; плоский `{id,type,media}` → «Field "media" must be of type Object»; без `id` → «Can't find field "id"». `tg_bot.py rich` загрузку в `media` пока не умеет — слать сырым запросом.
- Свой файл: положить в `media` и сослаться `![](tg://photo?id=cover)`. Работают
  `tg://photo|video|audio?id=` (10.2) и `tg://document?id=` (10.3). `id` — 1–64
  знака `[A-Za-z0-9_-]`. В `media` кладётся `InputMedia*`, то есть допустимы и
  `file_id`, и `attach://…` — **заливка нового файла прямо в этом же вызове**.
- Для рассылки это способ не тянуть картинку по внешнему адресу на каждого: залить
  один раз → взять `file_id` из ответа → дальше слать по нему. Путь документирован:
  «simply pass this file_id as a parameter instead of uploading. There are no limits
  for files sent this way», в `InputMedia*` file_id помечен «(recommended)».
  💭 Наш только шаг «залить, отправив файл самому себе».
  🚨 **`file_id` привязан к боту:** «the file_id field is tied to a single bot id, so
  your test instance cannot use a shared file_id database … files must be individually
  reuploaded». Черновик гоняли тестовым ботом, рассылку шлёт боевой — 💭 файл надо
  залить заново, иначе падает каждое сообщение рассылки.
- Подпись: заголовок после адреса `![](url "подпись")` или `<figcaption>`;
  авторство — `<cite>`. У `InputRichBlock*` подпись самого `InputMedia` игнорируется.

## 5. Кнопки внутри поста (10.3)

```html
<tg-button-row align="center">
  <tg-button type="url" style="primary" url="https://t.me/bot?start=src">Записаться</tg-button>
</tg-button-row>
```

В режиме `blocks` это `RichBlockButtons` / `InputRichBlockButtons`: `type="buttons"`,
поля `buttons` и `align`.

- Ряд — от 1 до 8 кнопок, выравнивание `left|center|right`; рядов может быть много.
- Кнопка может стоять и прямо в абзаце (`<tg-button>` внутри `<p>`).
- Типы: `url`, `callback_data` (1–64 байта), `web_app`, `login_url`,
  `switch_inline_query*`, `copy_text`, `disabled`.
- Стили: `danger`, `success`, `primary`, `link` (последний — только у callback).
  Приложение МОЖЕТ подставлять цвета фона и текста из своей темы по стилю («Apps may
  use theme-specific colors…»); конкретных цветов для rich-кнопок доки не называют —
  в отличие от `KeyboardButton`, где прямо «danger (red), success (green), primary
  (blue)». 💭 Отсюда вывод, что вид на клиентах может различаться.
- 🚨 **Ограничения, которые молча ломают пост:**
  - `web_app` — только личные чаты и **не** от имени бизнес-аккаунта;
  - `login_url` — не поддержан в эфемерных сообщениях; поле `bot_username` у `LoginUrl`
    в `RichMessageButton` не поддержано;
  - `switch_inline_query_current_chat` — **в каналах не работает вовсе**; все три
    `switch_inline_query*` не работают в direct messages chats и от бизнес-аккаунта.
- **Скрытую ссылку `[текст](url)` клиент открывает через подтверждение** «Open this
  link?» с полным адресом — оговорка сказана именно про inline link; голый URL,
  распознанный автоматически, открывается сразу. 📎 Про url-кнопки в доках ни слова, но
  по исходникам клиентов кнопка даёт **то же подтверждение** (Telegram Desktop
  `api_bot.cpp`: `HiddenUrlClickHandler::Open` для всех ботов, кроме верифицированных;
  Web A `openUrl` без `shouldSkipModal`). То есть «кнопка открывается сразу» — неверно;
  кнопкой призыв в рассылке лучше давать просто потому, что она заметнее.
- 💭 Промокод удобно дублировать кнопкой `copy_text` (копирует заданный текст,
  1–256 знаков; про промокоды в доках ничего нет). ❓ Причина — раздел 1: на Android
  текст rich не скопировать вовсе, на iOS не копируется код. Desktop старше 7.1 кнопку
  в теле поста не покажет (раздел 7), поэтому промокод оставлять и текстом.

## 6. Лимиты

32768 знаков · 500 блоков (считая вложенные, пункты маркированных и нумерованных
списков, строки таблиц, блоки цитат и блоки `<details>`) · 16 уровней вложенности ·
50 медиа · 20 колонок в таблице.

- в 32768 входят **альтернативный текст кастомных эмодзи и исходник формул**, а не
  только видимый текст;
- 16 уровней — вложенность **и блоков, и форматирования**. 💭 Как именно Telegram
  считает уровни, не сказано: по модели данных (`RichTextUrl.text` →
  `RichTextItalic.text` → `RichTextBold.text`) жирный внутри курсива внутри ссылки —
  три вложенные сущности; входит ли сам блок-абзац вокруг них, неизвестно, поэтому
  держать запас в один уровень.

📎 **После примерно 8000 знаков клиент сворачивает пост кнопкой «Show More».** В
справочнике API этого порога нет (в Rich Message Limits только пять чисел выше), но
цифру называет сам Telegram в блоге 11.06.2026, `telegram.org/blog/watch-apps-and-more`:
«up to 32,768 characters now, with a merciful Show More button after the first 8,000 or
so». Порог приблизительный и клиентский, через API не проверяется — правило вёрстки:
главное и кнопку держать выше него.

## 8. Отступы и читаемость

**Настроек отступа в API нет вообще** — ни `margin`, ни `padding`, ни межабзацного
интервала: у `RichBlockParagraph` только `type` и `text`. Единственный параметр
отступов во всём rich — `is_compact` у таблиц, и он их только уменьшает.
📎 На трекере висит открытое предложение добавить абзацам выравнивание (/c/64662,
Suggestion, Open) — значит, его тоже нет.

Чем управлять ритмом:

1. **Абзац = пустая строка.** 🚨 Одиночный перенос строки склеивается в пробел, как
   в обычном markdown. Жёсткий перенос внутри абзаца — 🧪 два пробела в конце строки
   (проверено отправкой: в дереве блоков появляется `\n`). Про `<br>`: своей строки в
   списке тегов у него нет, он встречается только в примерах внутри `<blockquote>` и
   `<blockquote expandable>` — но весь перечень тегов там и есть один блок примеров,
   поэтому фраза «Only the tags mentioned above are currently supported» его НЕ
   исключает. 💭 По типам он скорее сработает и в абзаце: `RichBlockParagraph.text` —
   тот же `RichText`, что у цитаты, а узла «перенос строки» в `RichText` нет.
2. **`---` между секциями** — единственный документированный визуальный разрыв.
3. **Мелкие заголовки** `####`–`######` вместо жирной строки.
4. **`<details>` и `<blockquote expandable>`** — убрать второстепенное под раскрытие.
5. 🧪 **Распорка из неразрывного пробела** — пустой абзац с `&nbsp;` / U+00A0.
   Документацией не обещана, но работает: Telegram сохраняет такой абзац блоком.
   Проверено 14.09.2026. Осторожно: после КАЖДОГО абзаца отступы выходят слишком
   большими (Данила, 11.09), по смысловым блокам — нормально (владелец, 14.09).
   💭 Раз это отдельный блок-абзац, каждая распорка съедает единицу из лимита в 500
   блоков (сам предел живой отправкой не проверяли).
   🚨 Проверять побайтово (`0xa0`), что в файл попал именно U+00A0, а не обычный пробел:
   на глаз они неразличимы, а обычный пробел распорку не даёт.

## 9. 🚨 Грабли, пойманные на живых отправках

- 🧪 **Хэштег в начале строки становится заголовком.** `#иитрансформация_осень2026`
  отдельной строкой пришёл блоком `heading` (`RichBlockSectionHeading`) крупным шрифтом
  и БЕЗ решётки. Лечится экранированием `\#…` — 🧪 тогда это обычный абзац, а хэштег
  остаётся сущностью `hashtag`. 🚨 Из доков это НЕ выводится, а даже наоборот: заявлена
  совместимость с GFM, а GFM требует пробел после решётки и `#hashtag` считает абзацем.
- **В нашем пути «markdown без `media`» картинка идёт только по ссылке**: «Media blocks
  support only HTTP and HTTPS URLs», а `tg://photo?id=…` без поля `media` ссылаться
  не на что. Файл по ссылке качает сам Telegram («Telegram will download and send the
  file»), поэтому хост обязан быть доступен ЕГО серверам: 🧪 с S3 REG.RU превью не
  собирается (`WebPageEmpty`, 11.09), прошедший боевую отправку хост —
  `your-product.example/companyyour-project/covers/` (14.09). Это ограничение СПОСОБА, а не API:
  через поле `media` файл загружается прямо в вызове (раздел 4).
- **Разметку можно проверить ДО рассылки, не глазами:** отправить себе с
  `disable_notification`, распечатать `result.rich_message.blocks` по типам и сразу
  `deleteMessage`. Дерево покажет, склеились ли строки, стал ли хэштег заголовком,
  распознана ли картинка (блок `photo`).
- **Как это выглядит — проверяется отдельно:** дерево блоков отвечает на «что понял
  сервер», а не «что увидит человек». Для второго есть официальный **@RichTextDemoBot**
  (документирован на `/bots/features`) и свой глаз на своём клиенте. Перед рассылкой на
  базу нужны обе проверки.
- 🧪 **Telethon отдаёт rich-сообщение с пустым `message` и `media=None` — но содержимое
  читается:** текст лежит в `m.rich_message.blocks` (Telethon 1.44, LAYER 227;
  проверено чтением с сервера 31.07.2026 — 27 блоков, включая `PageBlockTable`).
  «Пустым» rich выглядит только в наших обёртках: `tg_client.py read-chat` поле
  `rich_message` не печатает.

## 10. Рассылка rich по базе

**Лимиты Telegram, которые действуют одновременно:**

| Лимит | Значение |
|---|---|
| в ОДИН чат | избегать больше **1 сообщения в секунду**: короткие всплески сервер *может* пропустить, но в итоге пойдут 429 |
| в группу | не больше **20 сообщений в минуту** |
| массовая рассылка | около **30 сообщений в секунду** суммарно |
| при 429 | в `parameters.retry_after` приходит, сколько секунд ждать 💭 |

💭 Связку «429 → `retry_after`» доки прямо не пишут: API описывает поле как «In case of
exceeding flood control, the number of seconds left to wait before the request can be
repeated», а FAQ отдельно говорит, что при превышении лимитов «you'll begin receiving
429 errors».

🚨 💭 Первый лимит задеть легче всего: текст-спутник и rich-пост, ушедшие одному
человеку подряд, — это больше одного сообщения в секунду в один чат. Гарантии 429 на
втором нет (FAQ допускает всплески), но в рассылке пара уходит КАЖДОМУ — это уже не
всплеск, а вдвое больший темп. Держать между парой паузу от секунды либо слать двумя
проходами по базе. Рассыльщик обязан спать `retry_after` и повторять именно это
сообщение, а не зашивать в код «30/сек».

Тем, кто не включает платные рассылки, FAQ советует растягивать рассылку:
«consider spreading them over longer intervals (e.g. 8-12 hours) to avoid hitting the
limit» — 8–12 часов там приведены ПРИМЕРОМ, а не нормой; на странице API этого нет.

**Платный режим (`allow_paid_broadcast`) — не закладываться:**

- включается в @BotFather, поднимает потолок до 1000 сообщений/с;
- 🚨 **первоисточники расходятся в пороге входа:** страница API — «In order to **use**
  this feature, a bot must have at least **10,000 Stars** on its balance»; Bots FAQ —
  «In order to **enable** this feature, a bot must have at least **100,000 Stars** on
  its balance **and** at least **100,000 monthly active users**». Проверено грепом
  обеих страниц 15.09.2026: на странице API слов про число пользователей нет вовсе.
  Расходятся не только цифры — FAQ описывает ВКЛЮЧЕНИЕ фичи, API её ИСПОЛЬЗОВАНИЕ;
- платятся **не все сообщения**, а только те, что сверх бесплатных 30/с, и только
  **успешно отправленные** («only charged for messages that are broadcasted
  successfully» — платится успешный вызов, а не подтверждённая доставка получателю).
  Прикидка «получатели × 0,1 Star» неверна: рассылка на 1800 человек в темпе ≤30/с
  стоит 0 Stars.

**Порядок боевой рассылки:**

1. сухой прогон — убедиться, что флаг rich реально доехал до отправителя (🧪 у нас был
   случай, когда `--rich` не передавался в `main()`, и база получила бы звёздочки);
2. 💭 проба себе и второму человеку, глазами (чем проверять — раздел 9);
3. 🚨 **сохранять `chat_id` + `message_id` каждой отправки в лог.** `editMessageText`
   правит адресно, пакетной правки в API нет — ни одного метода вида `editMessages`:
   чтобы исправить опечатку у 1800 получателей, нужно 1800 вызовов. ❓ Что правки тратят
   тот же флуд-бюджет, в документации не написано — это ответ разработчика Telegram
   («Limits for message editing and sending are shared», levlam, tdlib/td#3034).
   💭 Узнать `message_id` задним числом в Bot API нечем: методов чтения переписки нет;
4. 💭 текст-спутник и кнопка должны нести весь смысл для тех, кто видит заглушку.
