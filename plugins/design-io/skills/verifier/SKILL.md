# Verifier

Скилл делает **три разные работы** — ниже они разведены по режимам. Не путай их:
режим 1 открывает HTML в браузере, режим 2 судит чужую работу, режим 3 проверяет выводы по данным.

Плюс матрица ниже — точка входа в полную предсдаточную проверку: какие ещё скиллы звать,
в каком порядке и под какой тип артефакта. Без неё это 5-8 угадываемых вызовов подряд.

## Матрица: тип артефакта → набор проверок

Порядок один: дешёвое и блокирующее раньше дорогого. Время — грубая оценка прогона.

| Тип | Обязательно, по порядку | По желанию |
|---|---|---|
| Лендинг / сайт | режим 1 (5 с) → `license-check` (1 с) → `a11y-audit` (10 с) → `perf-audit` (40 с) | `i18n-stress-test` при локализации, `screenshot-test` |
| Слайды / дек | режим 1 → `license-check` | `screenshot-test`, если дек правят регулярно |
| Дашборд / отчёт с цифрами | режим 1 → **режим 3** (QA данных) → `a11y-audit` | `perf-audit` на больших таблицах |
| Прототип с состояниями | режим 1 → `states-checklist` (чтение, 0 с) → `proto-smoketest` → `a11y-audit` | `screenshot-test`, `i18n-stress-test` |
| Локальное приложение с dev-сервером | `webapp-testing` (поднимает сервер и ходит по UI) → `a11y-audit` → `perf-audit` | `proto-smoketest`, `screenshot-test` |
| Публикуемое наружу | набор своего типа + `license-check` и `leak-scan` — блокирующие | `perf-audit`, если это своя страница на домене |

Строка про dev-сервер существует по технической причине, а не для полноты: `verify.mjs`
резолвит аргумент как **путь к файлу** (`pathToFileURL`) и `http://localhost:5173` не
принимает. Приложение, которое надо сперва поднять (`npm run dev`, backend+frontend),
режим 1 проверить не может физически — там первым идёт `webapp-testing` с его
`~/.claude/skills/webapp-testing/scripts/with_server.py` (в этом скилле такого файла
нет — путь чужой), который держит серверы на время прогона. Обратное тоже верно:
готовый одиночный HTML гонять через webapp-testing незачем — поднимать нечего.

Почему так: режим 1 первый — по сломанной странице axe и Lighthouse врут, а не молчат.
`license-check` и `states-checklist` дёшевы (статический DOM / чтение чек-листа), но ловят самое
дорогое в переделке: чужой шрифт и ненарисованные empty/error-экраны. `perf-audit` последний —
свой Chrome, дольше всех, и его советы бессмысленны, пока вёрстка меняется. `screenshot-test` вне
прогона: ему нужен baseline, он окупается со второго раза — место ему в CI.

Наборы npm разные (`@axe-core/playwright`, `lighthouse`, `jsdom`, `@playwright/test`,
`pixelmatch`+`pngjs`) — ставь под выбранную строку, а не весь список.

### Четыре скилла «проверить перед сдачей» — разводятся по входу

Все четыре запускают Playwright и делают скриншот, поэтому по фразе «протестируй»
подходят одинаково. Выбирает не формулировка, а **что ты кладёшь на вход**:

| Что на входе | Скилл | На какой вопрос отвечает |
|---|---|---|
| один готовый файл на диске | `verifier`, режим 1 | «оно открывается и не сыплет ошибками?» |
| dev-сервер, который надо поднять | `webapp-testing` | «приложение стартует и UI отзывается?» |
| список сценариев, которые не должны отвалиться | `proto-smoketest` | «путь до цели проходится?» |
| эталонная картинка в репо | `screenshot-test` | «картинка не поехала?» |

Отсюда же следует, когда какой бесполезен. `screenshot-test` на первом запуске не
проверяет ничего — эталона ещё нет, он его создаёт, и окупается со второго раза;
место ему в CI, а не в предсдаточном прогоне. `proto-smoketest` нечего покрывать на
статичном деке без переходов. `verifier` не увидит логическую ошибку в цифрах — для
этого режим 3 ниже.

## Режим 1. Headless-чек HTML (основной)

Открывает результат в Playwright headless, проверяет:
- console errors / warnings
- невыполнившиеся network requests
- наличие ключевых элементов (опционально через селектор)
- размер документа (не пусто ли)

И сохраняет один скриншот **первого экрана** для визуальной самопроверки: в скрипте
`fullPage: false`, viewport по умолчанию 1440×900, флага «вся страница» нет. Для длинного
лендинга это один экран из нескольких — поднимай `--height`, если нужен весь лист.

### Зависимости (проверить ДО первого прогона)

Скрипт — node-Playwright, и его браузеры отдельные от python-Playwright: то, что
питоновский скрипт в соседнем скилле открывает страницы, ничего не доказывает.
Симптом расхождения — `browserType.launch: Executable doesn't exist at
…\ms-playwright\chromium_headless_shell-<build>\…` и exit≠0 при пустой `verify-out/`
(воспроизведено 22.08.2026: пакет требовал build 1232, в кэше лежали 1228 и 1234).

```bash
npm ls playwright || npm i playwright     # пакет (обычно уже лежит в ~/.claude/node_modules)
npx playwright install chromium           # браузер под ТЕКУЩУЮ версию пакета — обязательно
```

### Скрипт

`templates/verify.mjs` (лежит на диске, запускать по полному пути или из каталога скилла):

```bash
node ~/.claude/skills/verifier/templates/verify.mjs deck.html
# → verify-out/console.log + verify-out/screenshot.png
# Exit code: 0 если всё чисто, 1 если есть ошибки.
```

Опции:
- `--require-selector ".some-class"` — упасть, если элемента нет
- `--width 1920 --height 1080` — viewport
- `--wait 1000` — дополнительная задержка перед снимком
- `--out verify-out/` — куда писать

### Когда главный агент должен дёргать режим 1

1. Прототип / дек / макет готов.
2. Перед тем как писать «готово» в чат.
3. Если получит exit 1 — прочитать `console.log`, исправить, повторить.

Это **не** замена ручному просмотру пользователем — это санитарный фильтр, чтобы пользователь не открывал заведомо сломанное.

## Режим 2. Ревью чужой работы: анти-анкоринг и выбор лучшего варианта

Когда verifier зовут проверять результат другого агента/воркера (кросс-чек, ревью артефакта):

1. Сначала сформируй **свой** вердикт: прогони verify.mjs, собери свой список проблем по артефакту.
2. Только потом читай отчёт/самооценку автора и сверяй.

Чтение чужих выводов до собственной проверки анкерит на их версии — получаются «подтверждающие» проверки вместо независимых. Драфт своего вердикта ДО чтения чужого — обязательный порядок.

### Выбор лучшего из вариантов + GAN-паттерн

Когда verifier сравнивает 2+ результата воркеров (или adversarial-review решает «оставить/откатить»):
LLM-судья предпочитает первый вариант — прогоняй ОБА порядка A-vs-B и B-vs-A, оставляй кандидата
только при перевесе голосов, а не по самоотчётной цифре. Генератор не оценивает свою работу.
Полный паттерн (двусторонний pairwise против position bias, скептик-оценщик, crash-proof apply ladder) —
`references/gan-adversarial-improve.md`.

## Режим 3. QA аналитики данных

Когда на проверку приходит не HTML, а **выводы по данным** (отчёт, дашборд, набор SQL, слайд
с цифрами), console-ошибок не будет — сломанный анализ выглядит нормально и просто врёт.
Порядок тот же: свой вердикт до чужого отчёта. Чек-лист перед отдачей, каталог ловушек
(размножение строк на JOIN, неполный период, сдвиг знаменателя, среднее от средних, часовые
пояса, отбор по результату, черри-пикинг окна), способы независимого пересчёта, красные флаги
и трёхуровневый вердикт — `references/data-analysis-qa.md`.
