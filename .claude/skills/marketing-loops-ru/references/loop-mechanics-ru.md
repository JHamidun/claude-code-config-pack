# Механика петель: state, идемпотентность, шаблон авторинга

Идемпотентность реальна, только если петля помнит между прогонами, что уже сделала. Иначе она действует дважды, re-nag'ает тех же людей и пере-алертит те же проблемы.

## Где живёт state

Один state-файл на петлю:

```
~/.claude/loops/<имя-петли>.json     # память петли (локальные петли Claude Code)
~/.claude/loops/<имя-петли>.log      # append-only лог прогонов
```

- Петли на **своём сервере** (cron/n8n поверх своих БД) — state в JSON рядом со скриптом или таблицей в той же БД.
- Петли у **ботов agent-fleet** — state в runtime-директории бота (их cron уже имеет свой контекст).
- Если планировщик даёт свой dedupe/cursor — используй его. Суть — долговечный state, не конкретный файл. Никогда только в памяти: петля, забывающая при рестарте, повторит себя.

## Что хранить

```json
{
  "loop": "churn-signal",
  "last_run": "2026-07-18T09:00:00+03:00",
  "cursor": "2026-07-17T23:59:59+03:00",
  "handled": ["user_1042", "user_1077"],
  "cooldowns": { "user_1042": "2026-08-01T00:00:00+03:00" },
  "in_flight": ["exp_pricing_v3"],
  "counters": { "user_1042_attempts": 2 }
}
```

- **cursor / watermark** — до какого момента обработано; смотреть только новее.
- **handled** — dedupe-ключи уже обработанного.
- **cooldowns** — окна подавления на сущность (не контактировать внутри окна).
- **in_flight** — открытые действия (бегущий тест, активная интервенция) — не начинать конфликтующее.
- **counters** — счётчики попыток для стоп-условий («после 2 win-back писем — стоп»).

Держи state маленьким: чисти handled/cooldowns после истечения окон. **Никогда не логируй сырые ПД** (email, телефон, имя) в state и логах — только внутренние ID или хэши (152-ФЗ + здравый смысл).

## Паттерны идемпотентности

- **Watermark**: обрабатывать только новее cursor; продвигать cursor в конце успешного прогона. Безопасно пере-запускать.
- **Dedupe-set**: перед действием проверить ключ в handled; добавить после действия.
- **Cooldown-map**: перед контактом проверить cooldowns[entity]; установить после.
- **In-flight guard**: перед неперекрываемым действием проверить in_flight.

## Лог прогонов

Одна строка на прогон, действовала петля или нет — это аудит-трейл и детектор vanity-петель:

```
2026-07-18T09:00+03  checked=312  acted=2   note="2 подписчика newly at-risk, интервенции staged"
2026-07-19T09:00+03  checked=298  acted=0   note="no action"
```

Минимум: timestamp, сколько проверено, сколько действий, короткая заметка. Отвечает на два вопроса:
- **Vanity-петля?** Недели acted=0 и никто не скучает — или действует каждый прогон (гонится за шумом) — пересмотреть.
- **Дабл-действие?** Два прогона по одной сущности = dedupe/cooldown сломан.

## Сброс и бэкфилл

- **Сброс**: чистить cursor/handled, но **сохранять cooldowns** — иначе сброс заспамит недавно контактированных.
- **Первый прогон** (state ещё нет): watermark = «сейчас», НЕ обрабатывать всю историю — иначе петля отработает по каждому историческому элементу (например, зашлёт welcome-цепочку всей базе подписчиков). Нужен бэкфилл — сначала dry run (лог что бы сделала, действий ноль) с уважением кулдаунов.

# Шаблон авторинга новой петли

Прежде чем авторить — sanity-check, что это вообще петля (см. «Когда НЕ зацикливать» в SKILL.md): рекуррентная, сигнальная, не требует человеческого суждения по стратегии на каждом прогоне.

## Бланк (копируй)

```markdown
### Петля <имя>
- **Каденция**: <как часто смотрит — под скорость сигнала, не под желание апдейтов>
- **Действует когда**: <условие действия — что должно быть истинно чтобы ДЕЛАТЬ, а не проверить и пропустить. Большинство прогонов должны пропускать.>
- **Назначение**: <ОДИН исход, который петля двигает>
- **Скиллы**: <какие скиллы оркеструет каждый прогон>
- **Тело**:
  1. <шаг — обычно: выгрузить данные / diff с прошлым прогоном>
  2. <шаг — что пересекло условие действия>
  3. <шаг — драфт или stage ответа>
- **Самопроверка**: <верификация ДО действия — сигнал реален vs шум/сезонность/сломанный счётчик? Выборка значима?>
- **State**: <что помнит между прогонами — last-run, dedupe, кулдаун, handled — чтобы не действовать дважды>
- **Stop / bail-out**: <когда пропускает, останавливается, эскалирует, отключает себя — и поведение при ошибке. Чекпоинт перед всем, что тратит или публикует.>
- **Выход**: <куда идут результаты — файл, staged-черновик, отложка, отчёт, тред бота>
```

## Наводящие вопросы (по порядку)

1. Какой исход это защищает или растит? → *Назначение*
2. Как быстро реально меняется сигнал? → *Каденция*
3. Что должно быть истинно, чтобы стоило действовать? → *Действует когда*
4. Какие данные читает и что производит? → *Тело* + *Выход*
5. Что заставит действовать по ложному сигналу? → *Самопроверка*
6. Что обязана помнить, чтобы не повторяться? → *State*
7. Когда стоп, skip или handoff человеку? → *Stop / bail-out*

Не можешь конкретно ответить на 5, 6 и 7 — петля не готова.

## Пример (пустое → заполненное)

```markdown
### Петля активации первого шага в продукте
- **Каденция**: Ежедневно
- **Действует когда**: Пользователь зарегистрировался 48ч назад, не открыл ни одного трека и ещё не в этой надж-последовательности.
- **Назначение**: Растить долю новых регистраций, дошедших до первой ценности (первый открытый трек).
- **Скиллы**: `onboarding-cro-ru`, `html-email`, продуктовая БД
- **Тело**:
  1. Регистрации ~48ч назад и их статус первого трека.
  2. Фильтр: ноль открытых треков, нет активного наджа.
  3. Драфт таргетного письма «с чего начать» (рекомендация трека под указанные интересы, ссылка на первый практикум, предложение помочь).
- **Самопроверка**: «Не открыл» — реальный гэп активации или гэп трекинга (события не пишутся)? Сверить с логами сервера до отправки.
- **State**: Кто вошёл в последовательность; suppression открывших трек; один надж на пользователя на стадию.
- **Stop / bail-out**: После 2 наджей без открытия — стоп, передать в широкую re-engagement петлю. Пайплайн событий stale → пропустить прогон целиком.
- **Выход**: Staged-письмо на пользователя + дневной счётчик новых активаций.
```

Что делает её безопасной: **самопроверка** защищает от письма активным из-за бага трекинга, **state** не даёт re-nag, **stop** ограничивает попытки и передаёт дальше вместо вечного цикла.

## Ship-чеклист

- [ ] Все 9 частей заполнены — особенно самопроверка, state, stop.
- [ ] Каденция соответствует скорости сигнала.
- [ ] Спроектирована так, что **большинство прогонов ничего не делают**.
- [ ] Всё, что **тратит или публикует** — за человеческим чекпоинтом (или явные капы+allowlist).
- [ ] State предотвращает дабл-действие и re-nag.
- [ ] Есть error-path (stale data → «stale», не выдумывать движение) и ручной off-switch.
- [ ] Планирование выбрано: /loop / /schedule / CronCreate / your-server cron / cron бота флота / ручная каденция. Тяжёлое локальное — только через ресурс-гард (реестр heavy-jobs).

Через несколько циклов задай вопрос vanity-петли: если по выходу никто не действует — удали.
