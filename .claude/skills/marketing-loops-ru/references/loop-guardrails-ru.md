# Guardrails и комплаенс петель (RU)

Петли действуют по расписанию, часто на данных клиентов, иногда с деньгами или публичным голосом. Применяй к каждой петле, которая **шлёт, тратит, публикует или трогает персональные данные**.

## Двухуровневая модель действий

**Уровень 1 — autonomous-safe** (петля может делать без присмотра):
читать данные, анализировать, диффать, скорить, **драфтить**, **ставить в очередь** (stage) на ревью.

**Уровень 2 — gated** (человеческий чекпоинт по умолчанию):
**тратить** деньги, **двигать** бюджет, **отправлять** сообщения, **публиковать** что-либо публичное, **удалять/подавлять** записи, **менять** живые настройки аккаунтов.

Действие уровня 2 бегает без по-штучной проверки, только если YourFirstName **явно авторизовал** это *и* оно ограничено капами + allowlist. Иначе — петля стейджит черновик, человек одобряет.

## Guardrails расходов (ad-fatigue, майнинг запросов, апсейл)

- **Жёсткие капы**: дневной/недельный потолок расхода, который петля не может превысить; halt + алерт при приближении.
- **Лимит изменения за прогон**: сколько бюджета можно двинуть за раз (≤20%), чтобы плохое чтение не перекроило всё.
- **Allowlist**: только указанные кампании доступны для автономных изменений; остальное — stage.
- **Направляющие**: судить платные изменения по выручке/ROAS (сквозная аналитика Метрика+ЮKassa), не по CTR/CPA — не оптимизировать прокси-метрику в убыток.

## Guardrails отправки и публикации (email, ТГ, PR, комменты, отзывы)

- **Дефолт — staging-очередь** + одобрение для всего публичного/исходящего. Авто-*драфт* — да; авто-*публикация* — нет (без явной авторизации). Для канала @yourchannel — только отложка на одобрение (`tg_client.py` send_as + schedule).
- **Капы объёма**: лимиты на прогон и на получателя — петля не может разослать по всей базе или зафлудить канал.
- **Suppression first**: перед любой отправкой проверять список отписок/do-not-contact.
- **Не авто-постить там, где кусаются детекция/ToS**: свои соцсети, питчи журналистам, ответы в чужих сообществах — stage для человека (бот-детекция + бренд-риск + лимиты Telegram Bot API).

## Комплаенс (RU-контур)

- **152-ФЗ «О персональных данных»** (любая петля с ПД): обработка на законном основании, согласие на рассылки, хранение данных в РФ, право на отзыв согласия и удаление; минимизация — тянуть минимум ПД, не копить в state. Имя/фото/отзыв клиента = ПД: **публикация отзыва/кейса — только с согласием**.
- **38-ФЗ «О рекламе» + маркировка (ОРД/ЕРИР)**: рекламные креативы и посевы — пометка «Реклама» + токен erid через ОРД. Петли, генерящие рекламу (ad-fatigue, креативы), обязаны стейджить с полем «требуется маркировка», не публиковать сами.
- **Email/СМС-гигиена**: рабочая отписка в каждом письме, идентификация отправителя, немедленное и постоянное исполнение отписки, скраб suppression перед каждой отправкой.
- **ToS платформ** (соц-слушание, комменты, отзывы, парсинг): уважать rate-limits Telegram/VK, правила площадок отзывов, не скрейпить и не авто-действовать где запрещено.

Если петля не может подтвердить согласие, разрешение или совместимость с ToS — её стоп-условие: **не действовать**, stage для человека.

## Обращение с ПД

- Не логировать сырые ПД в state и логи прогонов — внутренние ID или хэши.
- Тянуть минимум ПД для решения; не хранить в state.
- Экспорты и черновики — не в расшаренные/синхронизируемые места без умысла. Всё наружу — через `leak-scan`.

## Список «всегда эскалировать»

Никогда полностью автономно — человеку независимо от авторизации:

- Негативные/кризисные упоминания бренда; ответы на жалобы и юр/мед/фин-чувствительное.
- Newsjacking-углы (вето-лист в каталоге) — одобрение до любого питча/поста.
- Дорогие/стратегические аккаунты (B2B-клиенты, корп-когорты, at-risk логотипы) — handoff_to_user.
- Аномалии **выручки** или **рекламного расхода** — флаг немедленно, не само-коррекция.
- Всё, что удалит данные или тронет большую аудиторию за раз.

## Kill switch

Каждой запланированной петле — ручной выключатель, плюс способ остановить **все** петли быстро (отключить cron/routine, или глобальный флаг, который тела петель проверяют). Задокументируй там, где петли запланированы (`~/.claude/loops/README` / реестр heavy-jobs / cron-конфиг бота). Петля, которую нельзя быстро остановить, — это liability.

## Чеклист перед запуском

- [ ] Каждое действие классифицировано: уровень 1 (авто) или 2 (gated).
- [ ] Действия уровня 2 стейджатся — или ограничены явной авторизацией + капами + allowlist.
- [ ] У петель расходов — жёсткий кап и лимит изменения за прогон.
- [ ] У петель отправки — проверка suppression и капы объёма.
- [ ] 152-ФЗ / 38-ФЗ+ОРД / ToS соблюдены; fallback = «не действовать».
- [ ] Ни одного сырого ПД в state/логах.
- [ ] Кейсы «всегда эскалировать» уходят человеку.
- [ ] Kill switch задокументирован.
