# Маркетинг-петли (RU)

Помогаешь строить **маркетинг-петли** — повторяемые маркетинговые воркфлоу, которые агент (Claude Code сессия, routine, серверный cron или бот-агент) гоняет по расписанию. У каждой петли есть триггер, ограниченный набор шагов, самопроверка и явное условие остановки. Петля превращает задачу, которую делаешь руками и забываешь, в always-on систему: еженедельный скан SEO-возможностей по Вебмастеру, refresh выгоревших креативов, watch churn-сигналов подписки.

Петли — операционный кузен брейншторма: идеи говорят, *что попробовать один раз*; петли — *что продолжать делать по расписанию*, оркеструя остальные маркетинг-скиллы.

## Как использовать

**Сначала контекст:** собери контекст своего бизнеса (продукт + воронка) — петли обслуживают воронку `контент → trial/консультация → платный продукт/консалтинг` и её текущие дыры.

Затем:
1. **Определи работу петли.** Какой исход она защищает или растит? (позиции, эффективность рекламы, активация trial, удержание подписки, выручка, рефералы)
2. **Выбери петлю** из `references/loop-catalog-ru.md` — или адаптируй ближайшую.
3. **Настрой каденцию** под реальную скорость сигнала (правило каденции ниже).
4. **Согласуй человеческий чекпоинт.** Что петля делает автономно, а что ставит в очередь на одобрение владельца — `references/loop-guardrails-ru.md`.
5. **Запланируй** (раздел «Планирование» ниже).

Строишь несколько петель или целую операционку? Порядок внедрения — в конце `references/loop-catalog-ru.md` (начни с tracking + weekly review; не строй 20 сразу).

## Анатомия петли — 9 частей

Каждая петля в каталоге имеет девять частей. Авторишь или адаптируешь — заполни все: петля без стоп-условия, самопроверки или state — это не система, а способ делать неправильное по расписанию, повторно, тем же людям.

| Часть | Что определяет |
|-------|----------------|
| **Каденция проверки** | Как часто петля *смотрит* (еженедельно / ежедневно / по триггеру). Под скорость сигнала. |
| **Действует когда** | Условие действия — что должно быть истинно, чтобы реально *сделать*, а не проверить и пропустить. У здоровой петли большинство прогонов = «проверила, делать нечего». |
| **Назначение** | Один исход, ради которого петля существует. |
| **Скиллы** | Какие маркетинг-скиллы петля оркеструет на каждой итерации. |
| **Тело петли** | Упорядоченные шаги каждой итерации. |
| **Самопроверка** | Верификация *до* действия — чтобы не реагировать на шум, сезонность или сломанный счётчик Метрики. |
| **State / идемпотентность** | Что петля помнит между прогонами: last-run маркер, dedupe-ключ, окно кулдауна, множество «уже обработано». Без этого петли действуют дважды, re-nag'ают тех же людей, повторно алертят то же самое. Обязательно для всего, что по расписанию — `references/loop-mechanics-ru.md`. |
| **Stop / bail-out** | Когда петля пропускает, останавливается, эскалирует человеку или отключает себя — плюс поведение при ошибке. Нужен каждой петле, включая heartbeat (их stop = «ручное отключение + error-halt», никогда не «n/a»). |
| **Выход** | Куда идут результаты: файл, staged-черновик, отложка в мессенджер, отчёт, тред в форуме команды. |

Разделение **Каденция / Действует когда** критично: churn-петля может *проверять* ежедневно, но *действовать* только когда аккаунт пересёк порог риска и не контактировался внутри кулдауна. Смешение двух даёт петли, которые либо упускают окно, либо спамят.

## Правило каденции

Каденция — под реальную скорость изменения сигнала, а не под желаемую частоту апдейтов.

| Сигнал | Реалистичная каденция | Почему |
|--------|----------------------|--------|
| Позиции в Яндексе/Google, беклинки | Еженедельно | Двигаются медленно; ежедневные чеки — шум |
| Выгорание креативов, дрейф CPA (Директ/VK Ads/TG Ads) | Каждые 2–3 дня | Фидбек-циклы площадок — дни, не часы |
| Активация trial | Еженедельно | Нужно достаточно регистраций для значимости |
| Churn-сигналы подписки | Ежедневно или по триггеру | Окно раннего вмешательства короткое |
| Decay контента (портал, блог) | Ежемесячно | Эрозия трафика постепенная |
| Конкуренты (цены, позиционирование) | Еженедельно | Сдвиги редкие, но важные |
| Соц-слушание / упоминания | Ежедневно | Окна вовлечения закрываются быстро |

Сверхчастые петли — главный failure mode: плодят busywork и приучают игнорировать выход.

## Когда НЕ зацикливать

- **Настоящая работа — стратегия или креативное направление.** Петли поддерживают и оптимизируют; они не задают позиционирование и не придумывают кампании.
- **Действие публикует или тратит без ревью.** Авто-*драфт* поста/письма/креатива — ок. Авто-*публикация* и авто-*перекладка бюджета* — только через чекпоинт (или явная авторизация + капы + allowlist).
- **Сигнал слишком редкий.** Еженедельная конверсионная петля на 40 визитах/нед меряет шум.
- **Vanity-петля.** Если по выходу никто не действует — удали петлю. Петля, шлющая дашборд, который никто не читает, хуже чем ничего.

Для любой петли, которая шлёт, тратит, публикует или трогает ПД — применяй `references/loop-guardrails-ru.md` (двухуровневая модель, капы, 152-ФЗ/38-ФЗ/ОРД, список всегда-эскалировать, kill switch).

## Планирование (scheduling)

Тело петли агент-агностично; планирование зависит от среды:

- **Claude Code** — `/loop` (само-темп до условия), `/schedule` (cloud routines по cron), `CronCreate`. Тяжёлые **локальные** джобы (векторизация, батч-генерация) — ТОЛЬКО через ресурс-гард (idle-gate), никакого молчаливого крона на личной машине.
- **Серверный cron** — петли поверх серверных данных (продуктовая БД, аналитика) как cron-скрипт или n8n-workflow.
- **Агент-флот** — петля = cron-задача бота с постом в его тред форума команды. Аналитик-бот — сенсорные петли (weekly review, аномалии); рекламный бот — ad-fatigue и креативные. Тела петель из каталога — готовое топливо для их cron-конфигов (см. agent-builder tooling для механики cron у ботов).
- **Ручная каденция** — для петель с высокой долей суждения «прогоняй этот скилл каждый понедельник» — полноценная петля. Ценность в повторяемом *теле*, не в автоматизации.

Дефолт: cron по времени для review-петель (weekly review, ranking watch), динамический темп для monitor-until-threshold (churn watch, запуск).

## Авторинг новой петли

Если ничего не подходит — шаблон и ship-чеклист в `references/loop-mechanics-ru.md`. Заполни все 9 частей; не можешь конкретно ответить на самопроверку, state и stop — петля не готова к запуску.

Запускаешь петлю **без человека в цикле** (cron бота, `/schedule`, unattended `/loop`) — сначала `references/unattended-loop-patterns.md`: 7 продакшен-паттернов, rollout L1→L3 (старт всегда L1 Report), cost-модель и чек-лист безопасности (stop-условия, cost-cap, idle-gate через ресурс-гард, kill switch).

## Анти-паттерны

- Петля без стоп-условия → runaway-расход или бесконечный нагон.
- Одна каденция для всех петель → большинство бегает слишком часто и игнорируется.
- Без самопроверки → петля реагирует на шум, сезонность, сломанный счётчик.
- Без человеческого чекпоинта на spend/publish.
- 10 петель сразу → начни с одной, докажи что окупается, добавь следующую.

## Запрещённая лексика

«Поставил и забыл», «полностью автономный маркетинг», «ИИ делает всё сам», «10x на автопилоте», «машина роста». Петли — дисциплинированные системы с чекпоинтами, не магия. Описывай честно.
