# Auth-карта: как устроен вход (раздел 1 карты API)

Раздел «Auth» в карте обязателен: на нём ломаются клиенты чаще, чем на эндпоинтах. Шаблон строк — в
`api-map-template.md` (раздел 1). Здесь — как собрать ответы на эти строки и какие бывают схемы, на живых примерах
реальных сервисов. Сроки жизни ниже измерены на дату записи и меняются без предупреждения: свои сроки снимай заново
(`harvest.py capture` пишет их в `out/auth_hints.json`), а в карте ставь дату замера.

## Как заполнить за пять шагов

1. `python scripts/harvest.py capture --url <старт> --login-only` — один раз войти руками (2FA и капчу проходишь
   ты), профиль браузера запомнит сессию. Рядом ляжет `out/auth_hints.json`: черновик раздела без единого значения
   токена.
2. Прочитать `auth_hints.json` и сопоставить со строками шаблона:

   | Поле в `auth_hints.json` | Строка карты |
   |---|---|
   | `cookies[].expires_in`, `session_cookie` | Срок жизни (куки) |
   | `storage.*[].jwt.lifetime`, `jwt_paths` | Срок жизни и тип токена в `localStorage` |
   | `request_headers.authorization_schemes` | Тип (есть `Bearer` — токен; нет — смотри куки) |
   | `request_headers.custom_headers` (`x-*`) | Обязательные заголовки |
   | `request_headers.cookie_names_sent` | Какие куки реально уходят |
   | `auth_endpoints` | Как получить (эндпоинт сессии, ключи его ответа) |
   | `notes` | Готовые формулировки: «сессия на куках», «Authorization: Bearer» |

3. Определить тип по таблице ниже и записать «Признак протухания»: по нему клиент отличает «сессия умерла» от
   «ошибка в запросе». Один код 401 для этого мало (см. `troubleshooting.md`, раздел «Протухание»).
4. Проверить чистый HTTP: тот же GET без браузера, с теми же именами куки и заголовков. 200 — клиенту браузер не нужен.
   401, 403 или HTML — отвечает защита или не хватает заголовка, тогда запросы идут из страницы (`page.request`).
5. Записать «Чего не делать» (последний раздел файла) и «Сессий на учётку». Пустая строка читается через месяц как «не
   проверяли»: пиши «нет» с причиной.

## Схемы входа (образцы)

| Схема | Образец | Как получаем | Как протухает | Нюанс |
|---|---|---|---|---|
| Куки-сессия с коротким сроком | бухгалтерский веб-сервис: сессия живёт в куках; Bearer и своих заголовков нет | форма логина + 2FA | срок порядка двух часов, потом редирект на `/login…#error-session` | чистый HTTP живёт, пока жив токен; бандлы и сессия работают только в окне браузера (headless режется), поэтому клиент держит тёплый профиль и шлёт запросы из страницы |
| Bearer из эндпоинта сессии | админка веб-продукта на Auth.js: `GET /api/auth/session` с куками отдаёт `accessToken`, `user`, `expires`; дальше `Authorization: Bearer` | войти в браузере, из страницы `fetch('/api/auth/session', {credentials:'include'})` | срок токена порядка месяца | у Auth.js куку продлевает именно `GET /api/auth/session`: «продлить сессию» = дёрнуть его |
| Токен, скопированный из браузера руками | tl;dv: JWT из куки `tldvtoken`, порядка месяца; HeyGen web: кука `heygen_token` уходит заголовком `x-guest-session-token`, а не Bearer | DevTools → Application → Cookies, значение в `.credentials.master.env` | по сроку или при выходе из аккаунта | автоперелогина нет: клиент честно говорит «токен протух, возьми новый» и называет имя переменной |
| Долгоживущий refresh → короткий bearer | Suno (Clerk): кука `__client` живёт около года, `POST …/sessions/{id}/tokens` даёт `jwt`; Plaud: токены трёх сроков, WT живёт сутки, WRT около месяца; Codex OAuth `refresh_token` | refresh-секрет один раз из браузера | короткий токен протухает часто; клиент обновляет его сам по 401 | у Plaud протухание приходит и телом ответа (`status: -419` при HTTP 200): признак надо вносить в клиент |
| Токен из настольного приложения | Яндекс.Музыка: куки залогиненного приложения лежат на диске нешифрованными, скрипт подставляет их в браузер, страница авторизации приложения отдаёт OAuth-токен в адресе | один раз, дальше штатный API | сессия приложения протухла: откроется окно логина, заходишь руками | только своя учётка и своя машина; секрет — в `.credentials.master.env` (`YANDEX_MUSIC_TOKEN`) |
| Сессия на нескольких доменах с прогревом | Tilda: куки `tilda.cc`, `tilda.ru`, `feeds.tilda.ru`, `upload.tildacdn.com`; ленты оживают только после обхода страниц проекта в нужном порядке, иначе `{"error": "RELOGIN"}` (`tilda/references/auth.md`) | логин, затем обход страниц-рукопожатий | то же `RELOGIN` | строка «Прогрев сессии» в карте; маркер `RELOGIN` — в `EXPIRED_BODY_MARKERS` клиента |
| Куки браузера для подписанных запросов | Google Studio: `storage_state.json` Playwright, подпись SAPISIDHASH | вход в окне браузера | пока сессия жива, её продлевает скрипт автообновления; после `redirected to login` помогает только ручной вход | автообновление, стоящее в планировщике, может быть выключено: так сессия простояла мёртвой месяцами, и все маршруты, которые на неё опирались, молчали |
| Подписанная ссылка | бухгалтерский веб-сервис (скачивание счёта) и Plaud отдают URL с подписью вместо файла | запросить ссылку, качать сразу | порядка минут | заголовки авторизации к такой ссылке не нужны и вредны: скачивать без них, сразу после выдачи |

Пароль и код из письма — отдельные участники схемы: **2FA по почте** (бухгалтерский веб-сервис: шесть цифр; в списке писем код
обрезан, письмо читают целиком) автоматизируется чтением своей почты; **капчу** (Tilda: SmartCaptcha) не решают
программно: оставляют окно открытым, проходит человек.

## Одна сессия на учётку и живой демон прода

Часть сервисов держит на аккаунт **один** активный сеанс. Новый вход выбивает старый, и выбитым оказывается тот, кто
работает на самом деле: демон на сервере, вкладка человека, соседний процесс.

Образец — справочно-правовая система с одним сеансом на логин: страница `alreadyused` значит «сеанс занят».
Что стоит за правилом:

- Сессию держит демон на сервере. Локально **не** входить и **не** запускать скрипт логина: он выбьет демон.
- Признак вроде `recovering: true` в ответе демона значит, что он перелогинивается сам (ждёт 5, потом 10, потом 15
  минут). Живой демон не рестартят и не «помогают».
- На странице `alreadyused` ничего не нажимают: кнопки перехвата сеанса там нет, только форма обращения в поддержку.
- Тот же класс у Telegram: одна строка сессии Telethon на один процесс, два подключения отзывают ключ.

В клиенте это выражено так (`scripts/client_skeleton.py`): `SINGLE_SESSION = True` выключает автоперелогин по 401,
`--no-relogin` (или переменная `<СЕРВИС>_NO_RELOGIN`) выключает его на один запуск, а при `SINGLE_SESSION = True`
`login` без `--yes` только показывает, что сделал бы. Перед любым входом выясни, кто ещё держит сессию; в карте запиши это в «Сессий на учётку»
и «Чего не делать».

## Откуда клиент берёт токен

Токен, который клиент выдал себе сам (перелогин по 401 или `login`), лежит в кэше `~/.claude/.sessions/<сервис>.json`:
вне репозиториев, в файле только токен, время записи и короткий отпечаток токена из переменной (не сам токен).
Токен, который ты положил руками в `<СЕРВИС>_TOKEN`, клиент считает новее кэша, если значение в переменной изменилось
после записи кэша: тогда берётся переменная, а `doctor` в пункте `authentication` пишет, откуда токен (`session file` или
`env <ИМЯ>`). Хочешь начать с чистого листа: удали файл кэша, больше он ничего не хранит.

## Чего не делать

- Не логиниться с этой машины при живой сессии прод-демона, если сервис пускает одну сессию на учётку.
- Не гонять перелогин по кругу: на 401 одна попытка входа и один повтор запроса. Вторая подряд неудача означает, что
  вход изменился (2FA, смена пароля, бан): дальше работает человек.
- Не печатать и не сохранять значения токенов и кук: в карте, навыке, тестах и выводе — только имена переменных и
  сроки. Печать «первых 60 знаков токена» для отладки тоже утечка: пиши длину и срок.
- Не выгружать трафик с `--keep-secrets` в папку, которую видит git; выгрузки и профиль браузера всегда в
  `.gitignore`.
- Не подставлять чужие сессии и куки, не обходить капчу и оплату: этот навык про собственную учётку владельца.
