# Runbook — операционные процедуры

Флот на your-server (`ssh your-server`): 157 работающих контейнеров, ~30 агентов Hermes. Каждый агент — каталог `/opt/hermes-<name>/` с `docker-compose.yml`, внутри контейнера данные в `/opt/data` (`config.yaml`, `SOUL.md`, `logs/`, `cron/jobs.json`, `state.db`, `sessions/`). Проверено 2026-08-07.

Скилл даёт две вещи: **канон процедуры** (как её записать, чтобы её можно было выполнить в три ночи и откатить) и **готовые процедуры** под этот флот.

Смежное, НЕ дублировать здесь: базовые проверки сервера → skill `server-health`; конфиг/деплой/провайдеры/53 гочи Hermes и OpenClaw → skill agent-builder tooling; специфика контейнеров конкретного бот-рантайма → свой ops-навык (в пак не входит); мониторы → skill `uptime-kuma-ops`; откат правок в коде по changes-log → skill `rollback-changes`.

## Канон процедуры

| Секция | Что в ней | Провал, если |
|---|---|---|
| Триггер | наблюдаемый симптом или расписание | «когда что-то не так» |
| Preflight | что проверить ДО (доступ, свободное место, кто ещё правит) | пропущен |
| Точка отката | конкретный артефакт: имя бэкапа, git SHA, снимок конфига | «откатим как было» |
| Шаги | точная команда + ожидаемый результат + что делать, если не он | «перезапусти сервис» |
| Верификация | проверка ЭФФЕКТА, не факта выполнения команды | «команда прошла без ошибки» |
| Откат | шаги назад + проверка, что откат сработал | отсутствует |
| Эскалация | при каком условии остановиться и к кому | «разобраться» |

Правила, которые ломаются чаще всего:

- **Точку отката снимают ДО первого изменяющего шага.** Не «сделаю бэкап, если что-то пойдёт не так». Конвенция флота: `cp file file.bak-<повод>-$(date +%Y%m%dT%H%M%SZ)` — так уже лежат бэкапы в `/opt/hermes-*/`.
- **Верификация проверяет эффект.** «Контейнер Up 5 seconds» — это не «бот отвечает». Ожидаемый результат формулируется в наблюдаемых величинах: heartbeat свежее N секунд, реальный ответ в чат, HTTP 200 на живом эндпоинте.
- **Один владелец на процедуру.** Кто её правит и кому эскалируют — в шапке. Без этого runbook протухает первым же изменением инфраструктуры.
- **Журнал прогонов.** Дата, кто, что было ненормально. Три подряд «пришлось делать шаг вручную» = процедура устарела, а не оператор невезучий.
- **Правка процедуры — часть инцидента.** Если шаг не сработал и ты нашёл обход — дописать его в процедуру в тот же заход, пока помнишь.

## Опасные команды: чем заменить

PreToolUse-гард `~/.claude/hooks/bash-guard.js` блокирует снос работающего прода — **в том числе внутри `ssh your-server "..."`** (payload пересканируется теми же правилами) и внутри inline-кода интерпретаторов. Это не помеха, а подсказка: почти всегда есть неразрушающая форма.

| Заблокировано | Безопасная замена | Почему замена лучше |
|---|---|---|
| `docker rm -f <c>` | `docker stop <c> && docker rm <c>` | процесс получает SIGTERM и успевает закрыть БД/сессии |
| `docker compose down` | `docker compose stop` (снять) / `docker compose up -d --force-recreate` (перечитать env и конфиг) | не удаляет сеть и не рвёт связанные стеки |
| `docker compose down -v` | не заменяется — это удаление данных | только с явного «да» владельца |
| `docker volume rm` | сначала `docker run --rm -v <vol>:/d -v /opt/backups:/b alpine tar czf /b/<vol>.tgz /d` | том агента = вся его память и сессии |
| `docker system/builder prune` | точечно: `docker image rm <id>` по списку из `docker images -f dangling=true` | prune сносит и то, что ещё нужно другим стекам |
| `systemctl stop X` | `systemctl restart X` или `reload` | нет окна, когда сервис лежит и все про это забыли |
| `pm2 delete X` | `pm2 restart X` (часть сервисов крутится на pm2, а не в docker) | `delete` теряет конфигурацию процесса |
| `docker stop $(docker ps -q)` | цикл по явному списку имён | массовая форма гасит 157 контейнеров разом |

Обход гарда (`CC_HOOKS_OFF=1`) — не инструмент оператора. Если ситуация реально требует разрушающей команды, это точка эскалации к владельцу, а не повод снять гард.

**Гоча:** `docker restart <c>` перезапускает процесс, но **не перечитывает** `environment`/`env_file` из compose. После правки переменных — только `docker compose up -d --force-recreate`.

## P1. «Бот молчит»

**Триггер:** сообщение в бота уходит, ответа нет. **Точка отката:** на шагах 1-4 ничего не меняется — откат не нужен; он появляется с шага 5.

Диагностика идёт слоями снизу вверх, каждый слой отсекает половину причин.

```bash
B=hermes-<name>
# 1. Живёт ли контейнер и не перезапускается ли по кругу
ssh your-server "docker ps -a --filter name=$B --format '{{.Names}} {{.Status}} {{.RunningFor}}'"
# ожидание: Up <часы>. Up несколько секунд при старом RunningFor = crash-loop → шаг 2
```

```bash
# 2. Причина падения / что пишет гейтвей
ssh your-server "docker logs --tail 40 $B 2>&1"
ssh your-server "docker exec $B tail -30 /opt/data/logs/gateway.log"
ssh your-server "docker exec $B tail -30 /opt/data/logs/errors.log"
```

Что означают строки, которые видно чаще всего:

| В логе | Значение | Куда идти |
|---|---|---|
| `[Telegram] ... Bad Gateway ... reconnecting` затем `polling resumed` | сетевой всплеск, адаптер сам поднялся | это норма, не чинить |
| `polling heartbeat probe failed` без `resumed` | поллинг встал | P2 (рестарт) |
| `401 Unauthorized` | токен отозван | новый токен у @BotFather, затем P3 |
| `No API key found` / `Provider authentication failed` | ключ или провайдер | `hermes status` (шаг 3) → skill agent-builder tooling, раздел Provider Resolution Cascade |
| тишина в `gateway.log` за часы, а контейнер Up | процесс жив, работа встала | P2 |

```bash
# 3. Что агент реально считает своей моделью и ключами (а не что написано в config.yaml)
ssh your-server "docker exec -u 1000 $B /opt/hermes/.venv/bin/hermes status"
# ожидание: Model / Provider = то, что ждёшь; нужный ключ с ✓
```

```bash
# 4. Не занят ли токен вторым процессом
ssh your-server "docker ps --format '{{.Names}}' | xargs -I{} sh -c 'docker exec {} printenv TELEGRAM_BOT_TOKEN 2>/dev/null | sed \"s|^|{} |\"' | sort -k2 | uniq -f1 -d"
# ожидание: пусто. Две строки с одним токеном = два бота дерутся за getUpdates, отвечает то один, то другой
```

**Шаг 5 и дальше:** если слой найден — переходи в профильную процедуру (P2 рестарт, P3 конфиг, P4 крон). Если все четыре слоя чистые, а бот молчит — это не инфраструктура, а агент: смотри `agent.log` и сессию пользователя (skill agent-builder tooling).

**Верификация (общая для любого исхода):** написать боту со СВОЕГО аккаунта и дождаться настоящего ответа, а не отсутствия ошибки.

```bash
python ~/.claude/tools/tg_client.py send @<BotName> "тест 1"
python ~/.claude/tools/tg_client.py read-chat @<BotName> --limit 3
```

Нумеруй тесты («тест 1», «тест 2»…) — иначе после рестарта не отличишь свежий ответ от старого. Тестировать только со своих аккаунтов, не с чужих.

**Эскалация:** молчат ≥3 бота одновременно → это не боты, а общий слой (AI Gateway, сеть, диск) → P5 + P6.

## P2. Рестарт агента Hermes

**Триггер:** поллинг встал, процесс завис, после правки кода плагина.

**Preflight:** убедиться, что агент сейчас не в середине долгой задачи — `docker exec $B tail -5 /opt/data/logs/agent.log`.

**Точка отката:** запомнить, сколько контейнер прожил до рестарта (`docker ps` → `Status`) — если после рестарта он не проживает и минуты, это регресс, а не лечение.

```bash
B=hermes-<name>
ssh your-server "docker restart $B"          # правок в env НЕ было
# ИЛИ, если менялись config.yaml / env / compose:
ssh your-server "cd /opt/$B && docker compose up -d --force-recreate"
```

**Верификация** (по возрастанию строгости, проходить все три):

```bash
ssh your-server "docker ps --filter name=$B --format '{{.Status}}'"                  # 1. Up
ssh your-server "docker exec $B tail -5 /opt/data/logs/gateway.log"                   # 2. есть строка о подключении платформы
ssh your-server "docker exec $B cat /opt/data/cron/ticker_heartbeat"                  # 3. unix-время, свежее минуты
```

`ticker_heartbeat` — надёжнейший признак живости: планировщик пишет туда unix-таймстамп каждый тик. Значение старше нескольких минут при Up-контейнере = процесс жив, а внутренние петли встали.

Telegram-поллингу нужно 5-10 секунд после старта — первое сообщение, отправленное сразу, может утонуть.

**Откат:** рестарт сам по себе необратим и безвреден; откатывать надо то, ради чего рестартовали (см. P3).

**Эскалация:** контейнер уходит в crash-loop (`Restarting` в статусе) → НЕ перезапускать по кругу, снять `docker logs --tail 100` и разбирать причину; это уже не операционная процедура.

## P3. Правка config.yaml / SOUL.md агента

**Триггер:** смена модели, персоны, тулсетов, лимитов.

**Точка отката — обязательный первый шаг:**

```bash
B=hermes-<name>; TS=$(date +%Y%m%dT%H%M%SZ)
ssh your-server "docker exec $B sh -c 'cp /opt/data/config.yaml /opt/data/config.yaml.bak-$TS && ls -la /opt/data/config.yaml.bak-$TS'"
# ожидание: файл существует и ненулевой. Нет строки в выводе — СТОП, не править
```

**Шаги:** правка → `docker compose up -d --force-recreate` (не `restart`: правки env иначе не подхватятся).

**Верификация:** `hermes status` показывает новые значения **и** бот отвечает (P1, шаг верификации). Конфиг может примениться, а агент — сломаться на первом же ходу.

**Откат:**

```bash
ssh your-server "docker exec $B sh -c 'cp /opt/data/config.yaml.bak-$TS /opt/data/config.yaml'"
ssh your-server "cd /opt/$B && docker compose up -d --force-recreate"
# и снова полная верификация — откат тоже надо доказать
```

**Три ловушки этого флота (проверены прогоном внутри контейнеров, 2026-08-05):**
- Секция `personality:` верхнего уровня в `config.yaml` **мертва** — движок читает личности только из `agent.personalities`. Правка там ничего не делает, а выглядит как работа.
- `disabled_toolsets: [terminal]` **не** закрывает исполнение кода: остаются `code_execution` и `delegation`. Закрывать надо все три.
- `platform_toolsets` режется по каналу, а не по агенту: по крону возвращается полный набор инструментов.

**Никогда:** `chattr +i` на `/opt/data/cron/jobs.json` — планировщик сохраняет состояние через `os.replace()` и умирает с `PermissionError`. Иммутабельность только на `config.yaml` и `SOUL.md`.

## P4. Крон агента не отработал

**Триггер:** ожидаемое сообщение по расписанию не пришло.

```bash
B=hermes-<name>
ssh your-server "docker exec -u 1000 $B /opt/hermes/.venv/bin/hermes cron list"
```

Читать поля: `Next run` (в будущем?), `Last run … ok|error`, `Deliver` (`telegram:<chat_id>:<thread_id>`).

| Симптом в выводе | Причина | Действие |
|---|---|---|
| `Last run` протух на дни, `Next run` в прошлом | планировщик встал | сверить `ticker_heartbeat` (P2), рестарт |
| `Last run … ok`, но сообщения нет | неверный `Deliver` | для тем нужен `:thread_id`, иначе улетает в General; для приватных каналов — числовой ID, не @username |
| `Last run … error` | падает сама задача | `docker exec $B tail -50 /opt/data/logs/errors.log` |
| задания нет в списке вообще | не мигрировало/не создано | `hermes cron create` (skill agent-builder tooling) |
| все краны всех ботов упали в одно время | общий слой, не краны | P6, потом AI Gateway |

**Точка отката перед правкой расписания:**

```bash
ssh your-server "docker exec $B sh -c 'cp /opt/data/cron/jobs.json /opt/data/cron/jobs.json.bak-$(date +%Y%m%dT%H%M%SZ)'"
```

**Верификация:** `hermes cron` прогон задания вручную и получение сообщения в целевом чате. Дождаться следующего планового срабатывания и увидеть `Last run … ok` — обязательный второй заход, ручной прогон не доказывает работу расписания.

## P5. Место на диске

**Триггер:** порог 80% (`server-health` алертит от 80%). Замер 2026-08-07: 454G из 600G, 80%.

```bash
ssh your-server "df -h /; docker system df"
ssh your-server "du -sh /var/lib/docker/containers/*/*-json.log | sort -rh | head -10"
```

Разбирать в порядке «безопасное → рискованное», останавливаясь, как только порог отпустил:

1. **Логи контейнеров** — безопасно, обратимо потерей истории:
   ```bash
   ssh your-server "truncate -s 0 \$(docker inspect --format='{{.LogPath}}' <container>)"
   ```
   Профилактика: `logging.options.max-size: 50m` + `max-file: 3` в compose (правка = P3-дисциплина).
2. **Осиротевшие образы** — точечно, по списку:
   ```bash
   ssh your-server "docker images -f dangling=true --format '{{.ID}} {{.Size}}'"
   ssh your-server "docker image rm <id> <id>"
   ```
3. **Build cache** (31 ГБ на замере) и **prune** — массовое удаление, гардом заблокировано **обоснованно**: точка эскалации к владельцу, а не обход гарда.
4. **Старые бэкапы** `/opt/*/*.bak-*` и `/opt/backups` — удалять только после `ls -la` глазами: это единственные точки отката процедур P3/P4.

**Верификация:** `df -h /` ниже порога **и** контейнеры на месте (`docker ps -q | wc -l` = столько же, сколько до чистки).

**Откат:** удалённое не возвращается — поэтому порядок шагов именно такой. Если пришлось трогать пункт 4, сначала `tar czf` в `/opt/backups`.

## P6. Массовая проверка живости флота

**Триггер:** «что-то странное со всеми», после перезагрузки сервера, перед демо клиенту.

```bash
ssh your-server '
NOW=$(date +%s)
for c in $(docker ps --format "{{.Names}}" | grep ^hermes-); do
  HB=$(docker exec $c cat /opt/data/cron/ticker_heartbeat 2>/dev/null | cut -d. -f1)
  AGE=$([ -n "$HB" ] && echo $((NOW-HB)) || echo "-")
  ERR=$(docker exec $c sh -c "tail -3 /opt/data/logs/errors.log 2>/dev/null | tail -1" | cut -c1-70)
  printf "%-28s hb=%-8s %s\n" "$c" "$AGE" "$ERR"
done'
```

Проверено 2026-08-07: у живых агентов `hb` = 8-46 секунд. Читать: до ~120 — норма; сотни и тысячи — петли встали; `-` — планировщик не запускался. Правая колонка — последняя запись `errors.log` (там же WARNING-и, так что смотреть на дату: свежая = разбирать, недельной давности = шум).

Не найденные `docker ps` контейнеры и `Exited` — отдельный список:

```bash
ssh your-server "docker ps -a --filter status=exited --format '{{.Names}} {{.Status}}'"
```

**Эскалация:** одинаковая ошибка у ≥3 агентов = общий слой (провайдер, гейтвей, сеть, диск). Чинить слой, а не ботов по очереди — рестарты по одному в этой ситуации только маскируют причину.

## P7. Тяжёлая локальная задача

Любая процедура, грузящая ноутбук (векторизация, MinerU, ShadowBroker, демон-браузер), выполняется **только** через конвенцию `ваше локальное хранилище памяти`: idle-check, BELOW_NORMAL, GPU-check, чекпоинт, стоп-файл, TG-нотификации, ручной старт без крона.

Runbook для такой задачи не изобретает свой гард — он ссылается на реестр и добавляет ровно три вещи: **стоп-файл** (её точка отката), **как понять, что она реально идёт** (лог/чекпоинт, не факт запуска процесса), **что останется, если оборвать** (чекпоинт продолжит с места обрыва — или нет).

## Эскалация: когда остановиться

| Условие | Действие |
|---|---|
| Процедура не помогла с двух заходов | Стоп. Третий заход тем же способом — не диагностика. Собрать: логи, точное время, что менялось за сутки |
| Помогло, но непонятно почему | Записать в память и в процедуру. Невоспроизведённое лечение вернётся |
| Требуется разрушающая команда (prune, `down -v`, `volume rm`) | Владелец, явное «да». Гард здесь работает как задумано |
| Затронут клиентский контур (Company, Your-Brand и другие контуры заказчиков) | Сначала предупредить, потом чинить: у простоя есть адресат |
| Дело в общем слое (гейтвей, сеть, диск) | Не чинить ботов по одному — чинить слой |
| Утечка секрета в логе/томе | Ключ отозвать немедленно, только потом разбираться, как попал |

## Журнал

Каждая процедура ведёт свой журнал прямо в файле процедуры:

```markdown
| Дата | Кто | Что было ненормально |
|---|---|---|
| 2026-08-07 | YourFirstName | шаг 3 не нашёл heartbeat — у агента нет cron-секции, шаг сделан опциональным |
```

Пустой журнал за месяцы у процедуры, которую точно запускали, означает одно: её ведут в голове, и она уже разошлась с реальностью.
