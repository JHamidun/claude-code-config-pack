# Атрибуция и офлайн-конверсии

> Источник: «full funnel, оптимизация аналитики на масштабе», «работа с подрядчиками, атрибуция, динамика» — методология.

Server-side даёт **данные**, но без правильной атрибуции цифры не сходятся, и аналитика (тем более AI) бесполезна. дословно: **«Без качественных данных AI бесполезен»** — нужны корректная атрибуция, сходящиеся цифры, валидная воронка, контроль Unknown, правильные когорты.

---

## 1. Зачем атрибуция связана с CAPI

CAPI и офлайн-конверсии возвращают в кабинет **глубокие события** (квал-лид, оплата, LTV). Но кабинет должен ещё и **правильно отнести** их к источнику/кампании. Иначе:

- по **CPL** самая дешёвая кампания выглядит лучшей → льют бюджет туда (логика большинства маркетологов,;
- когда подтягиваются данные CRM (дозвонились, прошли квалификацию, длительность звонка, оплата, сумма сделки, возвраты) — **картина меняется**: дешёвые лиды почти не покупают, дорогие дают кратно больше денег.

**Полная воронка:**
```
Расходы → Клики → Лиды → Квал-лиды → Платящие → Первая выручка → LTV → Маржинальность
```
Решение «масштабировать или выключать» принимается по **когортной выручке**, а не по CPL. Некоторые каналы не окупаются в день 0, но окупаются на горизонте 3-6 месяцев.

## 2. Модели атрибуции

| Модель | Что считает | Когда |
|--------|-------------|-------|
| **Last Click** | конверсия → последнему клику перед ней | короткий цикл; базовая модель |
| **First Click** | конверсия → первому клику, который привёл пользователя | оценка верха воронки |
| **Multi-Touch (MTA)** | учитывает **несколько** точек взаимодействия | длинный цикл (B2B) — вклад каждого источника |
| **Last Non-Direct Click** | последний клик, исключая прямые заходы | короткий цикл, чтобы direct не «съедал» атрибуцию |
| **Last Non-Brand Click** | последний клик, **исключая брендовые** источники | когда брендовый трафик искажает картину |

**Правило выбора:**
- короткие воронки → **Last Click** / **Last Non-Direct Click** (что привело к последнему действию);
- длинные циклы (B2B) → **Multi-Touch Attribution** (вклад каждого источника в решение);
- если бренд искажает → модификация **Last Non-Brand Click**.

## 3. Офлайн-конверсии — связка по идентификаторам

Чтобы кабинет оптимизировался на квал-лиды/оплаты, **возвращаем глубокие события из CRM** с привязкой к исходному клику:

| Платформа | Механизм | Идентификатор связки |
|-----------|----------|----------------------|
| **Meta** | серверное событие (CAPI) — `Purchase` / кастомная конверсия | **External ID** + хеш email/телефон + **FBC/FBP** |
| **Google Ads** | импорт офлайн-конверсий + **Enhanced Conversions** | GCLID (из клика) / хешированные данные первой стороны |
| **Яндекс.Директ** | офлайн-конверсии в **Метрику** | **Client ID** (или Яндекс CID / по email/телефону) → Директ |

### External ID (Meta)
- Внутренний ID пользователя/лида (`user_id` из CRM), **стабильный** между браузерным и серверным событием.
- Захватывается при заходе/регистрации, сохраняется в CRM, прокидывается в CAPI при оплате.
- Детали хеширования и payload — `meta-capi.md`.

### Client ID (Яндекс)
- ID пользователя из Яндекс.Метрики, привязывается к лиду в CRM при заходе.
- Офлайн-конверсия (квал-лид/оплата) грузится в Метрику по Client ID → Директ видит, какие клики дали реальные деньги, и оптимизируется на них.
- Техническая загрузка через API — скилл `yandex`; методология — `yandex-direct-pro-ru` (раздел офлайн-конверсий).

### GCLID / Enhanced Conversions (Google)
- **GCLID** — Google Click ID, сохраняется с лидом → импорт офлайн-конверсии возвращает её к конкретному клику.
- **Enhanced Conversions** — хешированные данные первой стороны (email/телефон) повышают матчинг даже без GCLID.
- **server-side GTM** — единый серверный контейнер; консенсус курса: подключать однозначно («больше данных = лучше почва»), особенно при событиях вне веба.

## 4. Потери данных и сверка

Где теряются данные:
- **плохая настройка веб-аналитики** — нет корректных событий/UTM → неполная передача;
- **расхождения кабинет ↔ CRM** — рекламные системы и CRM показывают разные числа;
- **разные часовые пояса** источников → ошибки в отчётах.

**Лечится:**
- **единый часовой пояс** для всех источников (кабинеты, веб-аналитика, CRM) — обязательно;
- регулярные **сверки**: рекламные данные ↔ CRM;
- контроль числа **атрибутированных лидов и платящих**.

---

## 5. Пороговые значения (контроль качества)

| Метрика | Норма | Тревога |
|---------|-------|---------|
| **Доля атрибуции** | ≥ 95% | **< 95% → доп. проверки** |
| **Unknown source** | **1-10% — норма** | **20-40% — проблема** |

- **Частая критичная ошибка:** из отчёта **убирают** клиентов с неизвестным источником. Так делать нельзя — когда доля неатрибутированной выручки растёт, **доверие к аналитике падает**, но «прятать» Unknown = искажать картину.
- Растущий Unknown — сигнал поломки трекинга (часто — как раз отвал server-side/пикселя).
