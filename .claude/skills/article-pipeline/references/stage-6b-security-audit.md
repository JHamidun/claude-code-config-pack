# Стадия 6b — Security audit (гейт перед иллюстрацией)

> Отдельного агента у стадии нет: выполняется оркестратором инлайн (Bash + Read).
> Вынесена в отдельный файл, чтобы её не пропускали «за мелкостью» — это последний
> гейт перед тем, как текст уедет наружу.

## Вход / выход

- Вход: `<working_dir>/FINAL.md`
- Выход: `<working_dir>/SECURITY-SCAN.md`, вердикт PASS / BLOCK

## Запуск

Основной путь — сканер утечек из пака, он есть всегда:

```bash
python ~/.claude/skills/leak-scan/scripts/leak_scan.py <working_dir>
```

Свои имена, домены, почты и хэндлы задаются один раз в `~/.claude/leak-scan-identity.json`
(шаблон — `~/.claude/skills/leak-scan/scripts/identity.example.json`). Без него сканер
ловит только родовые формы секретов: ключи, токены, приватные IP.

Если установлен навык `habr-post`, у него есть более узкий скан под текст статьи:

```bash
python ~/.claude/skills/habr-post/templates/security_scan.py FINAL.md
# exit 0 = clean, 1 = leaks (список с line numbers)
```

Любая находка → **BLOCK**, возврат на стадию writer (именно на writer, не на editor:
формулировку надо переписать, а не подредактировать).

## Что смотреть глазами дополнительно

Скрипт ловит паттерны, а не смысл. Отдельно проверить:

- имена реальных людей и клиентов без разрешения на публикацию;
- внутренние URL, порты, хостнеймы, пути к приватным репозиториям;
- скриншоты и цитаты из внутренних кабинетов;
- ключи, токены, фрагменты конфигов;
- цифры, которые формально не секрет, но складываются в закрытую отчётность
  (выручка, число платящих, маржа) — если их не публиковал сам владелец бизнеса.

## Контур для текстов под договор с корпоративным заказчиком

Если статья пишется для клиента или по его теме, добавляются пять правил.
Они выглядят перестраховкой ровно до первого разбора с их службой безопасности.

1. Все отраслевые примеры — на синтетических данных либо явно помечены как учебные.
2. Не называть клиентов заказчика и не поминать его конкурентов в негативном ключе.
3. Про доступ к зарубежным сервисам — нейтральной формулировкой, без обсуждения
   способов обхода блокировок.
4. Чек-лист «что НЕ грузить в облачный ИИ» — в каждый текст про работу с данными:
   персональные данные клиентов (ФИО, ИНН, паспорт, телефоны, email) ·
   финансовая тайна (остатки, обороты, кредитные истории) · исходники внутренних
   систем · API-ключи и токены к корпоративным системам · скриншоты внутренних
   кабинетов и учётных систем.
5. Указывать корпоративные альтернативы: контур компании, локальные LLM,
   разрешённые в организации инструменты — иначе чек-лист читается как «нельзя ничего».
