# On-prem дообучение доменной модели (Unsloth)

> Когда нужна СВОЯ модель под домен/стиль/язык без облака: обезличивание + доменный дообуч. Дёшево (одна GPU), локально. Комплементарно приватному RAG — fine-tune даёт «знание в весах», RAG — «знание в контексте»; часто нужны оба.

## Когда fine-tune, когда RAG
- **RAG** — факты меняются, нужны источники/цитаты, свежесть. (Дефолт.)
- **Fine-tune** — стабильный стиль/формат/жаргон, доменная терминология, поведение (тон, структура ответа), сжатие латентности (меньше контекста). НЕ для «свежих фактов».
- **Оба** — доменная модель + RAG поверх = лучший enterprise-паттерн.

## Стек (одна GPU)
- **Unsloth** — 2× быстрее и ~×2 меньше VRAM для LoRA/QLoRA fine-tune (Llama/Qwen/Gemma/Mistral). 4090/A100 тянет 7B-30B в QLoRA.
- **Формат данных**: instruction-пары (`{instruction, input, output}`) или чат-шаблон; 500-5000 качественных примеров бьют 50k шумных.
- **LoRA/QLoRA** (не full fine-tune): адаптеры поверх замороженной базы — дёшево, быстро откатывается, несколько адаптеров под задачи.
- **Экспорт**: merge adapter → GGUF → Ollama/vLLM (тот же on-prem серверинг, что и RAG).

## Пайплайн
```
1. Собери доменный датасет (обезличенный — прогони через privacy-filter, чтобы ПД не попали в веса!)
2. QLoRA fine-tune через Unsloth (1-3 эпохи, следи за overfit на маленьком сете)
3. Eval на held-out доменных вопросах (см. verifier/references/rag-eval-opik.md — те же метрики)
4. Merge → GGUF → Ollama; A/B против базовой модели на реальных кейсах
```

## Критично
- **Обезличивание ДО обучения**: ПД/секреты в тренировочных данных → утекают в весах необратимо. Прогони датасет через on-device обезличивание перед fine-tune.
- Позиционный/размерный гард: маленький домен-сет → высокий риск overfit + «катастрофического забывания» общих навыков; держи LoRA-rank умеренным, эпох мало.
- Fine-tune НЕ добавляет свежих фактов — для них RAG. Не пытайся «зашить» меняющуюся базу знаний в веса.
