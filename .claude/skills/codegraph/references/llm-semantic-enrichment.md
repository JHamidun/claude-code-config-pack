# LLM-семантическое обогащение графа (overlay поверх codegraph)

> Источник паттерна: **Egonex-AI/Understand-Anything** (через @usefulrepa, 2026-07). НЕ установка — дистилляция подхода. У нас уже есть СТРУКТУРНАЯ половина (codegraph, 48 графов). Здесь — как доложить сверху СЕМАНТИЧЕСКИЙ слой, если задача требует «понять проект», а не «трейс вызовов».

## Зачем (разделение труда: структура vs смысл)

codegraph (tree-sitter → SQLite) даёт **детерминированную структуру**: символы, import/call-рёбра, callers/callees/impact. Он НЕ знает, что функция *делает*, к какому слою относится и какой бизнес-процесс закрывает. Understand-Anything показывает недостающую половину — **LLM читает распарсенную структуру + исходник и порождает смысл**. Две техники комплементарны, не конкурируют:

| Слой | Кто | Свойство | Стоимость |
|---|---|---|---|
| Структурный (что с чем связано) | codegraph / tree-sitter | детерминированный, воспроизводимый, офлайн | ~0 токенов |
| Семантический (что это ДЕЛАЕТ, зачем) | LLM (наши Fable-воркеры) | требует токенов, кэшируется на диск | платный, но одноразовый |

Правило: **структуру НЕ гоняем через LLM** (codegraph уже сделал точно и бесплатно). LLM тратим ТОЛЬКО на смысл, которого в графе физически нет.

## Что именно обогащение добавляет к нашему графу (4 артефакта)

Понятия Understand-Anything, переложенные на наш codegraph-вывод:

1. **Node summaries** — 1-2 строки на символ: «что делает эта функция/класс простым языком (RU)». Вход воркера: `codegraph node <name>` (исходник + caller/callee-трейл) → выход: краткое RU-описание.
2. **Architectural layers** — авто-классификация символа/файла в слой: `API · Service · Data · UI · Utility`. Даёт вид «сверху» без чтения кода.
3. **Domain view (бизнес-логика)** — маппинг `домен → поток(flow) → шаг(step)`: как код ложится на реальные бизнес-процессы. Самое ценное для CRM, LMS и ботов — связать `grantEntitlement()` с процессом «оплата → доступ».
4. **Guided tour / onboarding** — упорядоченный по зависимостям маршрут по ключевым узлам: «с чего начать читать этот репо». Заменяет ручной онбординг-док.

Плюс из их пайплайна берём **graph-reviewer** как идею — отдельный проход валидации: битые рёбра, узлы-сироты, референсная целостность обогащённого JSON.

## Наш рецепт обогащения (адаптация под codegraph + Fable + RU)

НЕ ставим их плагин (TS/JS стек, свой tree-sitter, свой дашборд, свои `/understand*` команды — дублирует то, что у нас уже есть структурно). Вместо этого — тонкий overlay поверх готового графа:

```
1. Структура (уже есть):  cd <папка-графа>/<проект> && codegraph status/files
                          → список файлов/символов = единица работы
2. Батч + параллель:      разбить символы на батчи 20-30 файлов, ≤5 Fable-воркеров
                          (их же лимит: 5 concurrent, 20-30/batch — совпал с нашим fable-параллелизмом ≤5)
3. Вход воркера:          `codegraph node <sym>` (исходник + трейл) — НЕ читать файл целиком,
                          граф уже дал точечный контекст (экономия 5-8× как в основном скилле)
4. Выход воркера (RU):    {symbol, summary_ru, layer, domain, flow, step} — append на диск инкрементально
5. Сохранить рядом:       `.codegraph/enrichment.json` в папке графа (коммитить как их `.ua/…json`
                          → напарник читает смысл без повторного прогона LLM)
6. Ревью-проход:          отдельный воркер сверяет enrichment.json с `codegraph status`
                          (все узлы покрыты? битые ссылки? слои консистентны?)
```

### Инкрементальность (ключевой выигрыш по токенам)

Как у них «re-analyze only changed files»: обогащать ТОЛЬКО дельту. После `codegraph sync` сравнить mtime/хэш символов с `enrichment.json` → в LLM гнать лишь изменённые узлы. Первый прогон дорогой, последующие — почти бесплатны. Для 48 графов полное обогащение вслепую НЕ делать — только по запросу на конкретный проект (это по сути heavy-job по токенам, гнать осознанно).

### RU-вывод

`--language ru` у них = мы промптим воркера сразу на русском summary. Совпадает с нашим дефолтом (personality: RU-коммуникация, EN-код). Символы/имена оставляем как в коде, описания — RU.

## Когда применять (и когда НЕ надо)

- **Применять**: онбординг в незнакомый большой репо, «объясни архитектуру проекта X», «какой код за бизнес-процесс Y», хендовер проекта заказчику, аудит слоёв. Т.е. вопросы «ЧТО и ЗАЧЕМ», а не «кто вызывает».
- **НЕ применять**: «кто вызывает / что сломается / трейс» — это чистый codegraph, LLM тут лишний расход. Мелкий проект (проще прочитать 5 файлов). Одноразовый вопрос (обогащать весь граф ради одного ответа — нерентабельно, спроси точечно через `codegraph explore`).

## Что НЕ берём из Understand-Anything

- Их интерактивный веб-дашборд (Astro homepage) — у нас вывод в чат/артефакт по запросу, отдельный дашборд не нужен.
- Их мульти-плагинную обвязку (`.claude-plugin`/`.cursor-plugin`/`.copilot-plugin`) и `/understand*` слэш-команды — дублируют наш Skill+CLI-поток.
- Их собственный tree-sitter слой — у нас codegraph уже парсит 30+ языков и держит 48 графов; переезжать незачем.
- `--auto-update` post-commit хук — по нашему правилу «минимум hooks» (Python-хуки на частых событиях крашат Extension Host). Обогащение дёргаем вручную/по запросу.

## Итог одной строкой

codegraph = скелет (бесплатно, точно, офлайн). Этот overlay = мышцы (LLM-смысл: summary/слой/домен/тур, RU, инкрементально, ≤5 Fable, кэш в `enrichment.json`). Ставить плагин Understand-Anything не нужно — мы воспроизводим только его ценную половину поверх того, что уже построено.
