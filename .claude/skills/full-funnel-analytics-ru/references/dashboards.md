# One-screen дашборд + Predict LTV + 9-шаговый процесс

> Источник: экспертная методология «full funnel, оптимизация аналитики на масштабе» ([AnalyticsCompany]).

Когда воронка собрана и данные сходятся, нужны два инструмента управления: **короткий дашборд на один экран** и **повторяемый процесс еженедельного анализа**, который ведёт к перераспределению бюджета.

---

## 1. One-screen дашборд (на масштабе)

Когда бюджеты растут, важен **короткий отчёт, помещающийся в один экран** — чтобы принимающий решение видел всё сразу, без переключения вкладок.

```
┌────────────┬──────────────┬───────────────────┬───────┬─────┬─────────┬──────────────┐
│  AdSpend   │ Новые        │ Zero Day Revenue  │ ROAS  │ LTV │ Refunds │ Predict LTV  │
│            │ платящие     │ (выручка день 0)  │       │     │         │              │
└────────────┴──────────────┴───────────────────┴───────┴─────┴─────────┴──────────────┘
```

| Метрика | Что показывает | Зачем на экране |
|---------|----------------|-----------------|
| **AdSpend** | расход на трафик за период | знаменатель окупаемости |
| **Новые платящие** | сколько новых клиентов заплатили | рост базы |
| **Zero Day Revenue (ZDR)** | выручка в день привлечения | мгновенная отдача + база для Predict LTV |
| **ROAS** | выручка / расход | окупаемость здесь и сейчас |
| **LTV** | пожизненная выручка клиента | реальная ценность когорты |
| **Refunds** | возвраты | чистит «бумажную» выручку |
| **Predict LTV** | прогноз LTV когорты | решение масштабировать, не дожидаясь 6 мес |

> Тот же набор метрик считается на каждом из 4 уровней оптимизации (Канал → Кампания → Adset → Креатив) — см. `cohort-funnel.md`.

Инструменты под дашборд: Google Sheets (прототип), Looker Studio / Яндекс DataLens, Supermetrics (коннекторы выгрузок), сервис сквозной аналитики ([AnalyticsCompany]) или BI на DWH.

## 2. Predict LTV — не ждать полгода

Главная боль масштаба: **нельзя ждать 6 месяцев**, чтобы понять, окупается ли когорта. Решение — прогноз по короткому сигналу.

### Базовая формула

```
Predict LTV = Zero Day Revenue × коэффициент
```

- **Zero Day Revenue** — выручка когорты в день 0 (известна сразу).
- **коэффициент** — множитель из **исторических когорт** (насколько в среднем зрелая когорта вырастает относительно дня 0).

### Как считать коэффициент

1. Берём **прошлые когорты**, у которых уже есть полный LTV (например, дозрели за 180 дней).
2. Для каждой считаем `k = LTV_факт / Zero Day Revenue`.
3. Усредняем `k` по группе.
4. **Считаем k раздельно** там, где поведение отличается:
   - по **каналам** (трафик с разных источников по-разному дозревает);
   - по **тарифам / продуктам**.
5. Для новой когорты: `Predict LTV = ZDR_новой_когорты × k_соответствующей_группы`.

Иллюстративно:

| Группа | Средний ZDR | Средний LTV (факт) | k = LTV/ZDR |
|--------|-------------|--------------------|-------------|
| Канал A, тариф Pro | … | … | 2.4 |
| Канал B, тариф Base | … | … | 1.6 |

→ новая когорта канала A/Pro c ZDR = X → Predict LTV = X × 2.4.

### Когда ML, когда нет

> **В 99% случаев простого множителя достаточно.** Сложные ML-прогнозы LTV нужны **только при очень больших объёмах** данных. Не строй ML-модель там, где работает один коэффициент по когортам — это пустая трата времени команды.

## 3. 9-шаговый процесс еженедельного анализа

Аналитика нужна **не ради отчётов**, а ради перераспределения бюджета туда, где бизнес зарабатывает больше. Чтобы «отчёт ради отчёта» стал рабочим циклом, проходим 9 шагов:

```
1. Overview     — общее состояние бизнеса (верхнеуровнево: ROAS, выручка, расход)
2. [ребёнок]мика     — валовые метрики во времени (тренд, не точка)
3. Когорты      — поведение клиентов по неделям/месяцам
4. Каналы       — разбивка по источникам трафика
5. Кампании     — разбивка внутри каналов (вниз по уровням)
6. Аномалии     — проверка выбросов и поломок трекинга (рост Unknown, провалы конверсий)
7. Гипотезы     — что и почему менять (узкое место → гипотеза)
8. Изменения    — внести правки в бюджет/кампании/креативы
9. Эффект       — проверить результат на СЛЕДУЮЩЕЙ неделе
```

Ключевые принципы процесса:
- **сверху вниз**: от Overview к конкретному креативу, не наоборот;
- **гипотеза → изменение → проверка эффекта** — замыкаем цикл, не бросаем на «изменили»;
- на шаге «Аномалии» обязательно проверяем **Unknown-долю** и сходимость кабинеты↔CRM (см. `attribution.md`);
- результат каждого цикла — **перераспределённый бюджет**, а не PDF-отчёт.

## 4. Качество данных — предусловие дашборда

Дашборд и AI бесполезны без качественных данных. Перед тем как доверять цифрам:

- **корректная атрибуция** (правильная модель под цикл — `attribution.md`);
- **сходящиеся цифры** (регулярная сверка кабинеты ↔ CRM ↔ веб-аналитика);
- **валидная воронка** (все 12 шагов считаются);
- **контроль Unknown** (1-10% норма, 20-40% проблема — не прятать, а чинить);
- **правильные когорты** (по неделе/месяцу привлечения).

> Цитата урока: **«Без качественных данных AI бесполезен.»** Сначала данные — потом дашборд и автоматизация.
