# Декомпозиция монолитного промпта агента

Что делать, когда системный промпт агента разросся: как разрезать его на слои, что выносить в файлы, что в инструменты, как мерить результат. Читай по триггерам «агент разросся», «промпт раздулся», «декомпозируй промпт».

## Декомпозиция монолитного промпта

Типичная болезнь выросшего агента: системный промпт на 300-400 строк, 10-15 инструментов, пара суб-агентов, зашитых внутрь кода инструментов. Каждый кусок добавлялся осмысленно — плохо именно целое: всё это резидентно в контексте на каждом ходу, политики дублируются между промптом и инструментами, а делегирование прибито гвоздями вместо решения в рантайме.

### Лестница стоимости

```
дешевле, слабее  ◀───────────────────────────────────▶  мощнее, дороже

TOOL CALL                 SKILL                    SUB-AGENT
одна функция,             инструкции, которые      отдельный агент со своим
stateless,                агент подгружает         контекстным окном и своей
детерминированная         по требованию            целью
```

### Куда что выносить (разбор по единицам)

Пройди промпт и список инструментов и для КАЖДОГО куска вынеси один вердикт: `keep` / `code-exec` / `skill` / `sub-agent` / `delete`.

| Признак куска | Куда | Почему |
|---|---|---|
| «Всегда делай X перед Y», политика, пороги, шаблоны писем/алертов, структура отчёта, чек-лист, сезонный календарь | **skill** | Знание нужно в 1 задаче из 10 — грузиться должно по требованию, а не висеть в промпте всегда |
| Инструмент возвращает >2k токенов / выдаёт сырые строки таблицы / его вызывают в цикле по сущностям | **code-exec** | Считать над файлом в песочнице и печатать компактный JSON дешевле, чем листать данные вызовами |
| Одна детерминированная функция, маленький ответ, есть побочный эффект (запись в ERP/CRM, отправка) | **keep как tool** | Лестницу вверх поднимать незачем |
| Нужен свой контекст (полная история, длинный документ), СВОЯ цель, а наружу отдаёт мало | **sub-agent** | Тяжёлый контекст живёт у него, а не у координатора |
| Суб-агент, который по сути сортирует список или заполняет шаблон, и отдаёт одно число/строку | **НЕ суб-агент** | Это скилл + пара строк кода; агент здесь — чистые накладные расходы |
| Функция не про работу этого агента (поиск в вебе «на всякий случай», аналитика соседнего домена) | **delete** | Скоуп — тоже архитектурное решение |

Ключевой эффект: объём знания НЕ уменьшается — 400 строк промпта превращаются в ~400 строк скиллов. Меняется момент, когда они попадают в контекст.

### Типизированный контракт на стыке

Главная потеря при делегировании — когда суб-агент отдаёт прозу, а координатор её парсит «на глаз». Число теряется, а вместе с ним и политика, которая на нём висит.

- Скилл описывает КОНТРАКТ, а не реализацию: суб-агент обязан вернуть строгий JSON вида `{value, confidence, method, flags}`.
- Парсить строго: битый JSON — это ошибка, а не повод догадаться.
- Даунстрим-политика читает поля контракта: `confidence < 0.6` → эскалация человеку вместо автодействия; `flags` не выбрасывать.
- Фолбэк, если делегирование недоступно: считать самому и **занизить** confidence, чтобы сработала та же эскалация. Не притворяться, что число проверено.
- Анти-паттерн: в тексте написано «рост может быть ×3», а в числовом поле лежит непересчитанная база. Якорить надо число, не нарратив.

### Делегирование — решение рантайма, а не зашитая цепочка

Не прибивай «этот инструмент внутри дёргает суб-агента». Объяви координатору список вызываемых агентов (callable/managed sub-agents), а В СКИЛЛЕ пропиши явные условия развилки:

- **Path A (посчитать самому):** горизонт ≤ N, флаги «сезонность/промо» нули, задача рутинная → один Bash-вызов скрипта из скилла.
- **Path B (делегировать):** горизонт больше, взведён флаг, виден слом тренда → вызвать суб-агента, передав ему ССЫЛКУ/идентификаторы, а не сами строки истории.

Передавать суб-агенту сырые данные — значит платить за них дважды. Он сам достанет их у себя.

### Эвал на каждый шаг

Декомпозиция без замера — это вкусовщина. Порядок: **baseline → одно изменение → прогон подмножества задач → следующее изменение**.

1. Зафиксируй baseline ДО правок (весь набор, один раз) и сохрани отчёт.
2. Меняй по одному решению за цикл (снял дампящий инструмент / включил скилл / ввёл контракт).
3. Прогоняй только те задачи, которые это решение должно перевернуть, — полный набор гоняй редко.
4. Читай не только PASS/FAIL, но и транскрипт: считай вызовы инструментов по именам, а не оценивай «на глаз».

Типы грейдеров, которые стоит иметь (детали и шаблоны — skill `llm-evals`):

| Грейдер | Что проверяет |
|---|---|
| `exact_match` / `set_match` | Ответ против ground truth, посчитанного из исходных данных, а не из ответа модели |
| `numeric_tolerance` | Число в пределах ±X% от эталона + обязательное упоминание фактора (промо, сезон) |
| `action_taken` | Побочный эффект РЕАЛЬНО произошёл: строка в sink-файле/БД с нужным `sku`/`qty`; вариант `not_kind` — что агент НЕ сделал (не оформил заказ, а эскалировал) |
| `efficiency` | Ответ верный, но бюджет ходов/токенов превышен → отдельный статус «медленно», а не FAIL |
| `wall_budget` | Уложился ли по времени — для задач, где поздний правильный ответ бесполезен |
| `ranked_mention` | Целевая сущность в топ-N выдачи, а не просто «упомянута где-то» |
| `composite` | AND нескольких проверок: худший статус побеждает |
| `llm_judge` | Только там, где нет машинного критерия; всегда с рубрикой |

Метрика: `score = (PASS + ½·SLOW) / N`. Держи референс-диапазон по каждой задаче — разброс LLM ±несколько пунктов на прогон, иначе будешь гоняться за шумом.

### Цикл работы

`observe → diagnose → decide → verify`. На каждом цикле: посмотри реальный транскрипт → назови причину (сколько вызовов, где потерялось число, что дублируется между промптом и скиллом) → прими одно решение → перепрогони затронутые задачи.

### Анти-паттерны

- Суб-агент ради сортировки или подстановки в шаблон.
- Инструмент, который «на всякий случай» отдаёт весь справочник.
- Одна и та же политика в промпте И в скилле (расхождение — вопрос времени).
- Правка нескольких вещей за цикл — потом не разберёшь, что именно перевернуло эвал.
- Замер «стало лучше» без baseline-файла.
