# Многоагентные архитектуры и бриф на агента

> Про то, **как разложить задачу между агентами** и **как решить, нужен ли агент вообще**.
> Технику конкретных движков (Hermes, OpenClaw) смотри в `architecture-deep-dive.md`.

## Бриф на агента — шесть вопросов

Заполняется до того, как открыт редактор. Шестой вопрос — главный: он отсекает
задачи, где агент строится потому, что это интересно, а не потому, что иначе нельзя.

```
1. Какая проблема?
2. Почему это проблема?
3. Как решает?
4. Какой результат?
5. Какая ценность?
6. ПОЧЕМУ НЕЛЬЗЯ РЕШИТЬ БЕЗ АГЕНТА?
```

Разобранный на занятии пример (браузер с AI-функциями):

- **Проблема:** пользователь скачал браузер, но не использует; кто использует — не
  трогает AI-функции.
- **Почему проблема:** за привлечение заплатили, а на главную метрику эти люди не влияют.
- **Как решает:** берём данные клиента, рассказываем про AI-функции, конвертируем в
  активного; работаем по разным каналам.
- **Результат:** доля активных **с 50% до 70%**.
- **Ценность:** больше аудитория сейчас — больше доля рынка потом.

Если на шестой вопрос честного ответа нет — задача решается автоматизацией, а не агентом.
Граница простая: детерминированный сценарий без развилок по смыслу — это скрипт или n8n
(`n8n`); агент нужен там, где на входе неструктурированный текст и решение зависит
от его содержания.

## Одноагентная схема

```
Данные на входе → Агент → Данные на выходе
```

У агента четыре обязательных элемента: **инструкции · инструменты · граничные условия ·
хуки**. Хуков два вида — **Decision Hook** (точка, где решение уходит человеку) и
**Error Hook** (что делать при сбое инструмента). Отсутствие хуков — самая частая
причина, по которой агент «работает, но ему нельзя доверять».

## Когда одного агента не хватает

Три причины разделить систему на несколько агентов:

1. **Разные компетенции** — аналитик и копирайтер требуют разных инструкций и стиля.
2. **Слишком много контекста** — всё в один промпт не помещается или теряется.
3. **Ошибки и повторения** — один агент в длинной цепочке накапливает собственные ошибки.

Многоагентная схема: `Агент-Менеджер (оркестрация) → Агент 1 … Агент n`, и у каждого
свой набор инструкций, инструментов, граничных условий и хуков.

**Пример разложения** — маркетинговый отчёт на 20 страниц (трафик, воронка продаж,
финансы, рекомендации, инфографика):

| Агент | Роль |
|---|---|
| **Координатор** | ставит задачу, распределяет работу, проверяет и собирает финал |
| **Аналитик** | подключается к данным, делает выводы, строит таблицы и графики |
| **Бизнес-эксперт** | интерпретирует выводы аналитика, пишет рекомендации и риски |
| **Копирайтер** | переписывает под стиль и ясность, собирает связные разделы |
| **Дизайнер** | оформляет отчёт, визуализирует данные |

## Семь архитектур

| Архитектура | Как устроена | Кейс и состав ролей |
|---|---|---|
| **Иерархическая** | один начальник, остальные исполняют | **Маркетинговый отчёт:** Координатор · Аналитик · Бизнес-эксперт · Копирайтер · Дизайнер |
| **Модульная** | каждый агент независим, вызывается по API по мере надобности | **Анализ конкурентов:** Скрапер · Категоризатор · Аналитик трендов и дельт · Репортер |
| **Событийно-реактивная** | агенты реагируют на события, **глобального плана нет** | **Воронка продаж B2B:** Квалификатор · Ресёрчер · E-mail-агент · Sales-бот (назначает встречи) · Менеджер (следит за конверсией) |
| **Кооперативная** | общая цель, агенты делятся промежуточными результатами | **Генерация контента:** Редактор (тема) · SEO-аналитик (ключи) · Автор · Иллюстратор · Публикатор в CMS |
| **Гибридная** | смешение подходов под процесс | **Логистика:** Платёжный · Склад · Маршрутизатор · Поддержка · Аналитик. **Онбординг сотрудника:** HR-агент · Наставник · Куратор задач · Тренер · Проверяющий |
| **Task-based** | разложение по задачам конвейера | **Финансовая сверка:** Импортёр · Сверщик · Финаналитик · Бухгалтер · Инспектор подозрительных транзакций. **Кастомный отчёт клиенту:** Ассистент (принимает ТЗ) · Датагеттер · Редактор слайдов · **Оратор (скрипт презентации)** · QA-агент |
| **Децентрализованная / коммуникативная** | агенты общаются между собой без центра | **Запуск рекламной кампании:** Планировщик · Концепт-мейкер · Арт-директор · Медиабайер · Аналитик. **Поддержка 24/7:** Гридер (определяет тему запроса) · Решатель · Эскалатор · Логгер · Аналитик повторяющихся проблем |

### Как выбирать

Практическое правило читается прямо из таблицы: **иерархическая** — когда есть один
ответственный за результат артефакт (отчёт, документ); **модульная** — когда шаги
переиспользуются в разных процессах; **событийно-реактивная** — когда события приходят
извне и в непредсказуемом порядке (входящие лиды, тикеты); **кооперативная** — когда
агенты правят один общий объект; **task-based** — когда порядок шагов фиксирован;
**децентрализованная** — когда нужна отказоустойчивость и нет естественного центра.

Гибридная — это то, чем оканчивается большинство живых систем, но начинать стоит
с чистого типа: гибрид, собранный сразу, обычно означает, что задачу не разложили.

## Функциональная архитектура

Помимо ролей на агента описываются:

- **сегменты** — с кем он работает;
- **каналы с ограничениями** — где именно общается и какие там лимиты (лимиты
  LinkedIn, антиспам почты, ограничения Telegram);
- таблица **«профиль → фича»** — какому сегменту какая функция;
- таблица **«профиль → лучший промпт»** — какой промпт работает на каком сегменте;
- список **tool-calls** — что именно агент вправе вызвать.

Последний пункт — это и есть граничные условия в исполняемом виде: перечень
разрешённых вызовов, за пределы которого агент не выходит.
