# RAG-эвалюация и observability (E2E)

> Как доказать, что RAG-система реально работает, а не «вроде отвечает». Применять до продакшна и при регрессиях. Комплементарно `check-skill-solo` (фактчек текста) — здесь про качество RAG-пайплайна как системы.

## Что мерить (4 метрики RAG)
1. **Context Recall** — нужные факты попали в ретрив? (retrieval-полнота)
2. **Context Precision** — в контексте нет мусора? (retrieval-точность)
3. **Faithfulness / Groundedness** — ответ выведен ИЗ контекста, а не выдуман? (анти-галлюцинация)
4. **Answer Relevance** — ответ отвечает на вопрос? (полезность)

## Harness (LLM-as-judge, локально по подписке)
- Собери **golden set**: 30-100 пар «вопрос → эталонные факты/источники» из реальных запросов.
- Прогони пайплайн → на каждый ответ судья-LLM оценивает 4 метрики (0-1) с обоснованием.
- **Position-bias guard**: при парном сравнении вариантов гоняй ОБА порядка (A-vs-B и B-vs-A), keep только при перевесе голосов (см. `verifier/references/gan-adversarial-improve.md`).
- Инструменты-паттерны: Opik (CometML) — трейсинг + eval-дашборды; ragas — готовые RAG-метрики; promptfoo — матрица промпт×модель. Как паттерны, движок судьи — по подписке (Claude/Codex/Gemini), без обязательного npm/облака.

## Observability в проде
- Логируй на каждый запрос: retrieved chunks + scores, финальный контекст, ответ, метрики judge (сэмплом). Silent-failure = худший баг RAG.
- Алерты: падение Faithfulness (галлюцинации растут), рост «не найдено» (корпус устарел), скачок латентности.

## Гейт перед релизом
| Метрика | Порог (старт) | Ниже → |
|---|---|---|
| Context Recall | ≥0.85 | чинить чанкинг/ретрив |
| Faithfulness | ≥0.90 | усилить «отвечай только из контекста», CRAG-fallback |
| Answer Relevance | ≥0.80 | реранкинг, переформулировка запроса |

Правило: **не деплой RAG без golden-set прогона**. «Тесты проходят» ≠ «система отвечает верно» — прогоняй с включённой фичей на реальных вопросах.
