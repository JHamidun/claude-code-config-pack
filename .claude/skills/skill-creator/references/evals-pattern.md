# Evals-паттерн: шипить evals.json вместе с каждым скиллом

> Источник: coreyhaines31/marketingskills (MIT, 40K★) — у **каждого** из 46 продакшн-скиллов лежит `evals/evals.json`. Формат у нас уже определён в `schemas.md` (§ evals.json) и используется в цикле create/improve. Новое здесь — **практика**: evals не одноразовый артефакт итерации, а постоянная часть скилла, живущая рядом с SKILL.md.

## Суть паттерна

```
skills/<name>/
  SKILL.md
  references/...
  evals/evals.json     ← регрессионные тест-кейсы скилла, версионируются вместе с ним
```

- **3–6 evals на скилл**: типовой сценарий, «провокационный» (пользователь просит анти-паттерн — скилл должен отработать guardrail), диагностический («почему не работает X»).
- Каждый eval = `prompt` (реальная формулировка пользователя) + `expected_output` (проза: что должен сделать скилл) + список проверяемых утверждений (`expectations` у нас / `assertions` у Corey — синонимы, наш канон `expectations` по schemas.md).
- Ключевая ценность assertion-гранулярности у Corey: утверждения проверяют **поведение скилла, а не текст ответа** — «читает контекст-файл до вопросов», «отказывается от fake-scarcity», «включает stop/bail-out», «не использует запрещённую лексику». Это ловит регрессии при редактировании SKILL.md.

## Когда применять

1. **Новый скилл** — evals пишутся в рамках обычного цикла skill-creator (см. SKILL.md, шаг test cases) и **остаются в папке скилла**, не в workspace.
2. **Правка существующего скилла** — прогнать его evals как регрессию (Improve mode / `eval-viewer/generate_review.py`).
3. **Аудит каталога** — скилл без evals у которого сложное поведение (guardrails, запрещённая лексика, разведение с соседями) — кандидат на дописывание evals в первую очередь; тривиальным скиллам-обёрткам evals не нужны (не плодить формализм).

## Чем хорошие evals отличаются от плохих

| Плохо | Хорошо |
|-------|--------|
| «Ответ полезный и подробный» | «Читает yourname-marketing-context до вопросов пользователю» |
| Проверяет присутствие слов | Проверяет решение/отказ: «требует одобрение человека до публикации» |
| Один happy-path eval | + провокационный: «пользователь просит фейк-таймер → скилл отказывает и предлагает честные альтернативы» |
| expected_output повторяет SKILL.md | expected_output описывает поведение в терминах ЭТОЙ задачи пользователя |

## Живые примеры в каталоге

Первые скиллы с шипнутыми evals по этому паттерну: `marketing-loops-ru`, `referrals-ru`, `offers-ru`, `pr-outreach-ru`, `free-tools-lead-magnets-ru` (все — evals/evals.json). Оригинальные примеры Corey: `scratchpad/ninja-recon/gh/marketingskills/skills/*/evals/evals.json`.
